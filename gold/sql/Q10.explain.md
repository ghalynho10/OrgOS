# Q10 in SQL, clause by clause

Question: which people have worked on issues that block, depend on, duplicate, or
supersede issues assigned to other people, and which people are connected through those
relationships?

Both files read `model.issue` (`issue_key`, `project_key`, `assignee_key`, NULL when
missing) and `model.issue_link` (`link_id`, `from_issue_key`, `to_issue_key`,
`outward_label`, `inward_label`).

## The ruling this pair follows

Your ruling of 2026-11-02, recorded in the body of main repo commit `1d793bd`, ruling 4:
Q10 reading B, a flat list of people is the answer, and the step lists `issue`,
`issue_link` and `person`, with the qualifying source and target assignees.

## Which end is the source (checklist item 8)

A row of `model.issue_link` reads "from_issue_key outward_label to_issue_key", and the
same link read from the other end is "to_issue_key inward_label from_issue_key".

- An outward label `blocks`, `depends on` or `duplicates`: the reading note takes it on
  the source issue with the target in `outwardIssue`, so the source is `from_issue_key`
  and the target `to_issue_key`.
- The inward label `supersedes`: the note takes it on the source issue with the target
  in `inwardIssue`. In Jira, a link entry on issue A with `inwardIssue` B and inward label
  `supersedes` reads "A supersedes B", and the model stores that link from B, the outward
  side, to A. So the source is `to_issue_key` and the target `from_issue_key`.

Labels are matched exactly, never the link type name, and only these four in only these
directions: an inward `blocks` or an outward `supersedes` does not count.

## `Q10.answer.sql`

- `assigned`: **step 1**, the issues of the seven projects whose `assignee_key` is not
  NULL and not `""` (checklist item 6). The flagged bot set is empty for this corpus
  (spec 0006 AC-17), so no bot clause is written.
- `relation`: **step 2**, the qualifying links with their source and target, as read
  above.
- `qualifying`: **step 1** on both ends, both joined to `assigned`, and **step 3**, the
  two assignee keys differ. A link from an issue to itself has equal keys, so it drops.
- `SELECT DISTINCT q.source_person AS person_key`: **step 4**, the distinct source
  assignees (checklist item 5). A target assignee is in the answer only when that person
  is also a source assignee somewhere, as the note says.

The Q10 adapter turns each row into `person:<person_key>`. It adds and drops nothing.

## `Q10.sources.1.sql`

The known answer has one source step, with kinds `issue`, `issue_link` and `person`.

- The same `assigned`, `relation` and `qualifying` as the answer file: **step 1** to
  **step 3**.
- Two `SELECT`s joined by `UNION`: one row per end of each qualifying relationship, with
  that end's issue, the link and that end's assignee. So every source and target issue,
  every qualifying link, and both the source and the target assignees are in the step
  (ruling 4). These are the relationships whose source assignees **step 4** returns.
  `UNION` removes repeated rows; the step is read as sets either way.
