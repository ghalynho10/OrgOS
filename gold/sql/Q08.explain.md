# Q08 in SQL, clause by clause

Question: which unresolved issues depend on other unresolved issues, and what are the
complete dependency chains connecting them?

The file reads `model.issue` (`issue_key`, `project_key`, `resolution_name`, NULL when
missing) and `model.issue_link` (`link_id`, `from_issue_key`, `to_issue_key`,
`outward_label`), where a row reads "from_issue_key outward_label to_issue_key"
(checklist item 8).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`:
ruling 1, a complete one hop chain counts (`hops = 2` is metadata and sets no minimum);
ruling 2, each hop's step lists `issue_link` plus both issues of that hop, and several
links between the same two issues stay one path with all their link IDs in that hop.

## The answer layout

A path answer (spec 0011 AC-12, amended 2026-11-12): one row per chain, a `path` column
with the issue keys in order, and one list column per kind with one item per hop:
`issue_link` holds each hop's link IDs, `issue` each hop's two issue keys. There is no
sources file. The Q08 adapter adds the `issue:` prefix to each path key and turns each
row into one step per hop; it sorts, filters and fills nothing.

## `Q08.answer.sql`

- `unresolved`: **step 1**, the issues of the seven projects whose resolution is missing,
  NULL or exactly `""`, read as `coalesce(resolution_name, '') = ''` (checklist item 6).
- `hop`: **step 2**, the links whose `outward_label` is exactly `depends on` and whose
  two ends are both in `unresolved`. The label is matched, not the link type name, as the
  reading note defines "depends on" by `type.outward`. A row runs from
  `from_issue_key` to `to_issue_key`, the outward direction the note says to follow.
  `GROUP BY` the two ends makes several links between the same two issues one hop,
  with every link ID in `jsonb_agg` (ruling 2).
- `walk`: **step 3**, simple paths in the outward direction. The first part takes each
  hop as a one hop path, leaving out a link from an issue to itself. The recursive part
  adds one hop from the last issue of the path.
- `cardinality(w.path) < 6`: a path grows only while it has fewer than six issues, so it
  stops at five hops, the question's `max_hops` (checklist item 9).
- `SELECT ... w.links AS issue_link, (...) AS issue`: each hop's link IDs and its two
  issues, in path order (ruling 2).
- The two `NOT EXISTS` tests: **step 4**, complete chains only. The first refuses a path
  when a qualifying hop leads into its first issue from an issue not on the path, so no
  chain starts partway. The second refuses it when a qualifying hop leads out of its last
  issue to an issue not on the path. A one hop path passes both when nothing extends it
  (ruling 1).

## How a repeated issue is forbidden

`NOT h.dst = ANY(w.path)` in the recursive part: a hop is added only when its target is
not already on the path, and the first hop leaves out `src = dst`. So no path the walk
builds repeats an issue. The same `ANY(w.path)` test in step 4 means an extension back
onto the path does not count, so a chain that closes a loop is complete when nothing
else extends it, as the note's "without repeating an issue" says.

## How a chain past hop 5 is detected

The walk stops at five hops, but step 4's second test looks one hop further: for a five
hop path it asks whether a qualifying hop leaves the last issue for an issue not on the
path. If one does, the five hop path is a section of a longer chain and is left out,
which is what "a five-hop chain qualifies only if it cannot be extended" and "exclude
partial sections of longer chains" ask (checklist item 9). The first test does the same
at the start. A chain longer than five hops therefore returns nothing, never a five hop
piece of it.

## Checklist notes

No date bound applies (item 2), nothing is counted or summed (items 3, 7), no group is
listed (item 4). `GROUP BY` the two ends removes repeated hops (item 5). The only numbers
are the cap, read from `max_hops`, and array positions; no ID is written (item 10).

## The difference from the Cypher pair

None in meaning. SQL builds the hop list first, merging several links into one hop, and
then walks it; the graph matches paths of relationships and merges paths with the same
issues afterwards. A missing resolution is NULL here and an absent property in the graph;
both read it with `coalesce(..., '') = ''`.
