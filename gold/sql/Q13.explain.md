# Q13 in SQL, clause by clause

Question: for CLOV-108, list its sub-tasks with each one's assignee, status, and total
logged hours.

Both files read `model.issue` (`issue_key`, `project_key`, `parent_key`) and the sources
file also reads `model.logged_time` (one row per time entry: `history_id`, `issue_key`,
signed `seconds`). A child names its parent in `parent_key`.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`: ruling
5, a parent hop adds the kind `parent` holding the direct child keys, and Q13 lists
`issue`, `parent` and `time_entry`; ruling 8, the registered scope is all of CLOV and the
rest are conditions inside it. The same commit body says Q13's answer holds the sub-task
IDs only; assignee, status and total hours are not stored. So the answer file returns
keys only, and assignee, status and hours are not computed here.

## `Q13.answer.sql`

- `INNER JOIN model.issue AS p ON p.issue_key = c.parent_key WHERE p.issue_key =
  'CLOV-108' AND p.project_key = 'CLOV'`: **step 1**, the parent record, CLOV-108 in
  CLOV, and **step 2**, every direct child by the child's `parent_key`. One join is one
  hop, so a grandchild never counts. `CLOV-108` is named in the question, so the literal
  check allows it.
- No filter on assignee, status or time: the note says to include sub-tasks with no
  assignee or no qualifying logged time. **Step 3** to **step 5** read display values
  only, which the answer does not store.
- `SELECT c.issue_key`: each sub-task once, as `issue_key` is the table's key and each
  child has one parent.

The Q13 adapter turns each row into `issue:<issue_key>`. It adds and drops nothing.

## `Q13.sources.1.sql`

The known answer has one source step, with kinds `issue`, `parent` and `time_entry`.

- The first `SELECT`: **step 1**, the parent's own issue record in `issue`, with NULL
  `parent` and `time_entry` cells, which under AC-12 as amended on 2026-11-12 are no ID.
- The second `SELECT` over `child`: **step 2** and **step 3**, each sub-task's issue
  record in `issue` and its parent hop in `parent` (the child key, ruling 5).
- `LEFT JOIN model.logged_time AS t ON ... AND t.seconds > 0`: **step 4**, every positive
  entry on a sub-task (checklist item 7), the entries whose amounts **step 5** sums. The
  condition sits in the join, so a sub-task with no positive entry keeps one row with a
  NULL `time_entry`, and if no sub-task has one the kind still comes back as `[]`
  (checklist item 11). The flagged bot set is empty for this corpus (spec 0006 AC-17),
  so no bot clause is written.

## Checklist notes

No date bound applies (item 2). Nothing is counted or summed in the answer (item 3).
Every sub-task is a row whatever it holds (item 4). No path is built, so item 9 does not
apply. No number is written; the one ID is the key the question names (item 10).

## The difference from the Cypher pair

None in meaning. The graph reads the parent hop as a `HAS_PARENT` relationship from child
to parent and time entries as `LOGGED_TIME` relationships; its `OPTIONAL MATCH` keeps a
sub-task with no entry as SQL's outer join does.
