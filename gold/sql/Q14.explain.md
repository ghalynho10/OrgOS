# Q14 in SQL, clause by clause

Question: is every sub-task of CLOV-538 resolved?

Both files read `model.issue` (`issue_key`, `project_key`, `parent_key`,
`resolution_name`, NULL when missing). A child names its parent in `parent_key`.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`: ruling
5, a parent hop adds the kind `parent` holding the direct child keys, and Q14 lists
`issue` and `parent`; ruling 7, Q14 reading A, if the answer is no the sources are `[]`
under AC-32, and AC-32 governs over the note's sentence on counterexamples; ruling 8, the
registered scope is all of CLOV.

## `Q14.answer.sql`

- `FROM model.issue AS p ... WHERE p.issue_key = 'CLOV-538' AND p.project_key = 'CLOV'`:
  **step 1**, the parent record. `CLOV-538` is named in the question, so the literal
  check allows it.
- `LEFT JOIN model.issue AS c ON c.parent_key = p.issue_key`: **step 2**, every direct
  child by the child's `parent_key`. One join is one hop, so a grandchild never counts.
  The outer join gives one row even when there is no child.
- `count(c.issue_key) > 0`: **step 2**, at least one direct sub-task exists, as the note
  requires. `count`, not `sum`, so no child gives 0 (checklist item 3).
- `bool_and(coalesce(c.resolution_name, '') <> '')`: **step 3**, every child's resolution
  is present, not null and not `""` (checklist item 6). Over no child it is NULL, and
  `coalesce(..., FALSE)` reads that as not established.
- The `AND` of the two, `resolved`: **step 4**, the boolean, one row. With no sub-task, or
  no parent record, it is false, because the note's condition that a sub-task exists is
  not met.

The Q14 adapter takes the one `resolved` value. It changes nothing.

## `Q14.sources.1.sql`

The known answer has one source step, with kinds `issue` and `parent`.

- `parent` and `child`: **step 1** and **step 2**, as in the answer file.
- `answer`: **step 3** and **step 4**, the same boolean as the answer file.
- The two `SELECT`s, each with `WHERE a.yes`: when the answer is yes, the parent's own
  issue record in `issue` (its `parent` cell NULL, which under AC-12 as amended on
  2026-11-12 is no ID), and every direct child, resolved or not, its issue record in
  `issue` and its parent hop in `parent` (the child key, ruling 5). All children are
  listed, not an example, as the note says.
- When the answer is no, the file returns no rows, following ruling 7. With one sources
  file fixed by the layout, that is one step with both kinds empty rather than no step
  at all; this only matters if the answer is no.

## Checklist notes

No date bound applies (item 2). The one count is `count`, not a sum (item 3). No group
is listed (item 4). No path is built, so item 9 does not apply. The only number is the
one sub-task the note requires; the one ID is the key the question names (item 10).

## The difference from the Cypher pair

None in meaning. The graph reads the parent hop as a `HAS_PARENT` relationship from child
to parent and decides with `size(children) > 0 AND all(...)` over the collected
children; a missing resolution is an absent property there and NULL here, and both read
it with `coalesce(..., '')`.
