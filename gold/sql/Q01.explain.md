# Q01 in SQL, clause by clause

Question: for each of the seven projects, how many issues created between January 1 and
March 31, 2013 (UTC) are still unresolved and have no assignee?

Both files read only schema `model` as the reader login: `model.project` (one row per
project) and `model.issue` (one row per issue, its project in `project_key`, its assignee
in `assignee_key`).

## `Q01.answer.sql`

- `FROM model.project AS p` with `WHERE p.project_key IN (...)`: **step 1**, the seven
  project population, named exactly as the reading note names them. The rows of the
  result come from the project table, so a project is listed even when none of its
  issues qualifies.
- `LEFT JOIN model.issue AS i ON i.project_key = p.project_key AND ...`: an outer join.
  Every project row stays; an issue joins only when it meets every condition in the
  `ON` clause. The conditions sit in `ON`, not in `WHERE`, because a `WHERE` on `i`
  would drop the projects with no match and lose their zeros (checklist item 4).
- `i.created_at >= TIMESTAMPTZ '2013-01-01 00:00:00+00' AND i.created_at < TIMESTAMPTZ
  '2013-04-01 00:00:00+00'`: **step 2**, the half open interval `[start, end)`. The
  start is included and the end excluded, so an issue created at midnight on April 1
  is out. The `+00` offset makes each bound UTC whatever the session zone (checklist
  item 2).
- `(i.resolution_name IS NULL OR i.resolution_name = '')`: **step 3**, still
  unresolved. In `model` a missing resolution is `NULL`; the `= ''` part covers an
  empty name the reading note also counts as unresolved (checklist item 6).
- `(i.assignee_key IS NULL OR i.assignee_key = '')`: **step 4**, no assignee. A null
  `assignee_key` means the issue has no assignee edge (spec 0007 AC-14); `= ''` covers
  the empty string the reading note names.
- `count(DISTINCT i.issue_key) AS issues` with `GROUP BY p.project_key`: **step 5**,
  the count per project. `count` of a column counts its non null values, so a project
  whose join found no issue gets 0, not NULL (checklist item 3). `DISTINCT` counts each
  issue once even if a join repeated it (checklist item 5).
- `ORDER BY p.project_key`: a fixed order for reading only; `compare` sorts a map
  itself, so the order changes no score.

The Q01 adapter turns each row into `project:<project_key>` with its `issues` count. It
adds no project, fills no zero and sums nothing.

## `Q01.sources.1.sql`

The known answer has one source step, of kind `issue`: the qualifying issues.

- `SELECT DISTINCT i.issue_key AS issue`: one column named after the kind, one issue key
  per row. With no qualifying issue the result is empty and still has its column, so the
  step is kept as `issue: []`.
- The `WHERE` holds the same four conditions as the answer file: **step 1** (the seven
  projects), **step 2** (the UTC interval), **step 3** (unresolved), **step 4** (no
  assignee). These are the issue records **step 5** counts per project, so the answer
  and the sources describe the same set.

## The difference from the Cypher pair

None in meaning. SQL reads the assignee from the `assignee_key` column; the graph reads
it as an `ASSIGNED_TO` relationship. Both come from the same `model_int` edge table.
