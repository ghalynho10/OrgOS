# Q19 in SQL, clause by clause

Question: which five projects have the most issues directly linked to issues in other
corpus projects?

Both files read `model.issue` (`issue_key`, `project_key`) and `model.issue_link` (one
row per link: `link_id`, the table's key, with `from_issue_key` and `to_issue_key`).

## The rulings this pair follows

Your accepted plan of 2026-11-02, recorded in the body of main repo commit `25e339a`:
the scope is the seven projects, with the other conditions inside it, and Q19 is one
step: `project` holds only the returned projects, and `issue` holds the counted issues
plus the issues at the other end of their links, which may sit in a project that was not
returned. The reading note names the kinds `project`, `issue` and `issue_link`. The
standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q19.answer.sql`

- `corpus`: **step 1**, corpus issues with their current `project_key`.
- `cross_link`: **step 2**, direct links of any type (no label condition) whose two ends
  both join `corpus` and whose projects differ. `link_id` is the key of
  `model.issue_link`, so each link is one row, which is the deduplication by link ID the
  note asks for. A parent relation is not in `model.issue_link`, and one join is one
  link, so neither a parent relation nor a chain counts.
- `end_point`: direction is ignored, so each end of each link is listed in its own
  project. `UNION ALL` keeps repeats, which the `DISTINCT` count below removes.
- `counted`: **step 3** and **step 4**, `count(DISTINCT e.issue_key)` per project, each
  issue once in its own project however many qualifying links, linked issues or partner
  projects it has (checklist items 3 and 5). Only a project with at least one qualifying
  issue forms a group, as the note says only such projects enter the ranking.
- `ranked` and `WHERE r.place <= 5`: **step 4** and **step 5**, rank highest first with
  `rank()`, under which tied counts share a place, so `place <= 5` keeps the top five and
  every project tied with the fifth, or all of them when fewer than five qualify. The `5`
  is the question's own number (checklist item 10).
- `ORDER BY r.issues DESC, r.project_key`: rank order, with ties in key order.

The Q19 adapter turns each row, in the query's order, into `(project:<project_key>,
issues)`. It adds and drops nothing.

## `Q19.sources.1.sql`

The known answer has one source step, with kinds `project`, `issue` and `issue_link`.

- `corpus`, `cross_link`, `ranked`: the same conditions and cut as the answer (**step 1**
  to **step 5**).
- `end_point` here also carries the link and the other end of each end.
- `supporting`: the ends whose own project is returned, so only counted issues of
  returned projects and their qualifying links.
- The first `SELECT`: the returned project, each counted issue, and each qualifying link
  supporting it.
- The second `SELECT`: the issue at the other end of each of those links. It may sit in
  a project that was not returned; that project is not listed, since the `project`
  column only ever holds the returned project (the accepted plan). The columns repeat
  per row and are read as sets. No cell is NULL.

## Checklist notes

No date bound applies (item 2). No hours (item 7). Item 4: a project with no qualifying
issue is outside the ranking by the note's own rule, so no zero row is owed. No path is
built (item 9).

## The difference from the Cypher pair

None in meaning. The graph holds each link as one relationship carrying `linkId`, read
once from its start node to its end node; only link relationships carry `linkId`, so
`HAS_PARENT` never matches. SQL cuts with `rank() <= 5`; the graph sorts, takes the fifth
count (or the last when fewer than five qualify) and keeps every count at or above it,
the same set. The Cypher sources file first finds the returned projects in a
subquery and then reads their links, to stay inside the graph's transaction memory.
