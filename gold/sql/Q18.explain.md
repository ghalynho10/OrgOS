# Q18 in SQL, clause by clause

Question: which people appear in more than one project as reporter or assignee, and in
how many projects each?

Both files read `model.issue` only: `issue_key`, `project_key`, `reporter_key` and
`assignee_key` (the current reporter and assignee, NULL when the issue has none).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 2,
`project` is listed and holds the projects of the listed issues; ruling 3, `person` is
listed, returned people only, and Q18's one step lists `issue`, `person` and `project`.
The accepted plan: the scope is the seven projects, with the other conditions inside it.
The standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q18.answer.sql`

- `role`: **step 1** and **step 2**. Both branches keep issues whose current
  `project_key` is one of the seven. The first takes the reporter key, the second the
  assignee key. `coalesce(..., '') <> ''` drops a key that is missing (NULL in `model`,
  including a missing containing object) or exactly `""` (checklist item 6). The flagged
  bot set is empty (spec 0006 AC-17), so no bot clause is written. `UNION` merges both
  roles into one list of (issue, project, person), so a person who is both reporter and
  assignee on one issue is one row.
- `count(DISTINCT r.project_key) AS projects ... GROUP BY r.person_key`: **step 3** and
  **step 5**, the distinct projects per person across both roles, so many issues or
  both roles in one project add one project (checklist item 5). `count`, never `sum`
  (checklist item 3).
- `HAVING count(DISTINCT r.project_key) >= 2`: **step 4**, at least two distinct
  projects.

The Q18 adapter turns each row into `(person:<person_key>, projects)`. It adds and drops
nothing.

## `Q18.sources.1.sql`

The known answer has one source step, with kinds `issue`, `person` and `project`
(ruling 3).

- `role` as in the answer (**step 1** and **step 2**), and `returned`, the people kept by
  **step 3** and **step 4**.
- The final `SELECT DISTINCT ... INNER JOIN returned`: every issue where a returned
  person holds a qualifying role, in any of their counted projects, with that person and
  the issue's project. Joining on the returned person, rather than listing every key on
  those issues, means a reporter or assignee who is not returned is never listed as a
  person (ruling 3). The projects are the projects of the listed issues (ruling 2),
  which are exactly each returned person's counted projects. The columns repeat per row
  and are read as sets. No cell is NULL.

## Checklist notes

No date bound applies (item 2). No hours (item 7). Item 4: a person with fewer than two
projects is not a member of the answer, so no zero rows are owed. No path is built
(item 9). No number or ID is written beyond the seven project keys and the `2` of "more
than one project", both from the reading note (item 10). The sources step is large;
it stays well below the 200,000 row cap (`STORE_ROW_CAP`), and a cap hit would be a
named error, never a partial result.

## The difference from the Cypher pair

None in meaning. SQL reads the roles from `reporter_key` and `assignee_key` and drops a
NULL or `""` key; the graph follows `REPORTED_BY` and `ASSIGNED_TO`, which exist only
for a present key (spec 0006). SQL reads the project from `project_key`; the graph
follows `IN_PROJECT`.
