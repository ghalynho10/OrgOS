# Q04 in SQL, clause by clause

Question: for each project, how does the total time logged compare with the total original
estimates for its issues?

Both files read only schema `model` as the reader login: `model.project` (one row per
project), `model.issue` (`project_key`, `time_original_estimate_s` in seconds, null when
missing) and `model.logged_time` (one row per time entry: `issue_key`, signed `seconds`,
`history_id`).

## How the population is read

The reading note's population is the issues in the seven projects "with either logged time
or an original estimate". The query reads "logged time" by the note's own definition, at
least one positive entry, and "an original estimate" as an estimate that is present
(`IS NOT NULL`), so an estimate of 0 counts and that issue is one of the "issues
contributing zero" step 1 lists. The answer value does not depend on this reading: an
issue with no estimate and no positive entry adds 0 to both totals. The sources do.

## `Q04.answer.sql`

The `logged` step:

- `FROM model.logged_time AS t INNER JOIN model.issue AS i ON i.issue_key = t.issue_key`
  with `i.project_key IN (...)`: entries on issues of the seven projects; each entry joins
  its one issue, so each amount is summed once (checklist item 5).
- `t.seconds > 0`: **step 2**, positive entries only (checklist item 7, spec 0006 AC-15).
  The flagged bot set is empty for this corpus (spec 0006 AC-17), so no bot clause is
  written. Every issue with a positive entry is in the population, so this needs no
  population test.
- `sum(t.seconds)` with `GROUP BY i.project_key`: **step 3**, the logged total per project.

The `estimated` step:

- `i.project_key IN (...) AND (i.time_original_estimate_s IS NOT NULL OR EXISTS (... t.seconds
  > 0))`: **step 1**, the population as read above.
- `sum(coalesce(i.time_original_estimate_s, 0))` with `GROUP BY i.project_key`: **step 4**,
  the estimate total per project, a missing estimate as 0, as the note says. The two
  totals are summed in separate steps, so no estimate is repeated once per entry.

The final `SELECT`:

- `FROM model.project AS p LEFT JOIN logged ... LEFT JOIN estimated ... WHERE p.project_key
  IN (...)`: every one of the seven projects is a row, joined to its totals or to none
  (checklist item 4). The zeros come from the query, never the adapter.
- `coalesce(l.seconds, 0) - coalesce(e.seconds, 0) AS difference`: **step 5**, logged minus
  estimated, positive when logged time exceeded estimates. A project with no total gives
  0 for it, which is the note's "missing values contribute 0".
- `ORDER BY p.project_key`: for reading only; `compare` sorts a map itself.

The Q04 adapter turns each row into `project:<project_key>` with its `difference`. It adds
no project, fills no zero and does no arithmetic.

## `Q04.sources.1.sql`

The known answer has one source step, with kinds `issue` and `time_entry`: every issue of
the population, including those contributing zero (**step 1**), and every positive entry
on them (**step 2**).

- `FROM model.issue AS i` with the population test of the answer file: **step 1**.
- `LEFT JOIN model.logged_time AS t ON t.issue_key = i.issue_key AND t.seconds > 0`:
  **step 2**, an outer join, so an issue with no positive entry stays as one row whose
  `time_entry` cell is NULL. Under AC-12 as amended on 2026-11-12, a NULL cell is no ID and
  is skipped; the issue still counts in the `issue` column. The `seconds > 0` sits in `ON`,
  not `WHERE`, or the outer join would drop those issues.
- `SELECT DISTINCT i.issue_key AS issue, t.history_id AS time_entry`: one row per positive
  entry, or one row for an issue with none. The `issue` column repeats per entry and is
  read as a set.

These are the issues and entries whose amounts **step 3** and **step 4** sum and **step 5**
subtracts.

## The difference from the Cypher pair

None in meaning. The graph makes every project a row with `MATCH (p:Project)` and computes
each total in its own `CALL (p) { ... }` subquery, where SQL uses two grouped steps and
outer joins. A missing estimate is an absent property in the graph and NULL in SQL; both
`coalesce` it to 0. In the sources, SQL's outer join and the graph's `OPTIONAL MATCH` both
leave a null `time_entry` for an issue with no positive entry.
