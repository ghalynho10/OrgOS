# Q03 in SQL, clause by clause

Question: how many issues resolved in FE between April 1 and June 30, 2012 (UTC) were
closed after their due date?

Every file reads only `model.issue` as the reader login: one row per issue, its project in
`project_key`, its resolution in `resolution_name` and `resolution_date`, its due date in
`due_at`. Both dates are `timestamptz` in UTC; a date only due value was stored as
midnight UTC at the start of that day by the load (spec 0006 AC-18), which is exactly the
reading note's rule, so the query compares the columns as they are.

## `Q03.answer.sql`

- `FROM model.issue AS i WHERE i.project_key = 'FE'`: **step 1**, the FE population.
- `i.resolution_name IS NOT NULL AND i.resolution_name <> ''`: **step 2**, resolved and
  closed mean a resolution name that exists and is not empty. No status condition, as the
  reading note says (checklist item 6).
- `i.resolution_date >= TIMESTAMPTZ '2012-04-01 00:00:00+00' AND i.resolution_date <
  TIMESTAMPTZ '2012-07-01 00:00:00+00'`: **step 3**, the half open interval `[start, end)`
  with an explicit `+00` offset, so the bounds are UTC whatever the session zone
  (checklist item 2). A null resolution date fails both comparisons and drops out.
- `i.due_at IS NOT NULL AND i.resolution_date > i.due_at`: **step 4**, a present due date
  and a resolution strictly later than it. `>` and not `>=`: resolving at the due instant
  is not after it.
- `count(DISTINCT i.issue_key) AS issues`: **step 5**, each retained issue counted once;
  `count` gives 0, not NULL, when nothing qualifies (checklist item 3). One table, no
  join, so `DISTINCT` is a guard only (checklist item 5).

The Q03 adapter reads the one row's `issues` value as the number. The known answer has no
source steps, so there are no sources files and the adapter returns an empty step list
(checklist item 11).

## The stage files (the zero guard, checklist item 13)

`Q03.stage.1.sql` to `Q03.stage.5.sql` each return one integer, `issues`: the store's own
count of FE issues after the conditions of **step 1** up to **step n**, added one step at
a time in the order of the reading note, none added, dropped or merged.

- Stage 1: **step 1** only, every FE issue. It must be above 0, so the population a zero
  is counted over exists.
- Stage 2: adds **step 2** (a resolution).
- Stage 3: adds **step 3** (the UTC interval).
- Stage 4: adds **step 4** (a present due date, resolved strictly after it).
- Stage 5: **step 5** adds no condition; it is the count itself, so it holds the same
  conditions as stage 4 and returns the same set counted once each. It equals the answer
  file by construction.

The guard accepts the pair only when these five counts equal the graph's five.

## The difference from the Cypher pair

None in meaning. SQL reads the project from `project_key`; the graph follows
`IN_PROJECT`. Missing values are SQL NULLs here and absent properties in the graph, and
`IS NOT NULL` plus `<> ''` treat both the same way.
