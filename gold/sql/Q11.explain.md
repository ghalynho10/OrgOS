# Q11 in SQL, clause by clause

Question: which people are connected through shared issue assignments, reporting,
creation, and time logging, and which projects connect them?

Both files read `model.issue` (`issue_key`, `project_key`, `assignee_key`,
`reporter_key`, `creator_key`, each NULL when missing) and `model.logged_time` (one row
per time entry: `history_id`, `issue_key`, `person_key` the author, signed `seconds`).

## The ruling this pair follows

Your ruling of 2026-11-02, recorded in the body of main repo commit `1d793bd`, ruling 6:
Q11 reading A, the step lists `issue` and `time_entry`.

## `Q11.answer.sql`

- `population`: **step 1**, the issues of the seven projects.
- `holds_role`, its first three parts: **step 2**, the assignee, reporter and creator of
  each issue, each only when its key is not NULL and not `""` (checklist item 6). The
  flagged bot set is empty for this corpus (spec 0006 AC-17), so no bot clause is
  written.
- `holds_role`, its last part: **step 3**, the authors of positive time entries on the
  issue, `seconds > 0` (checklist item 7). `UNION` keeps one row per issue and person, so
  a person with several roles on an issue counts once.
- `shared`: **step 4**, an issue connects people when at least two distinct people hold
  a role on it (`count(DISTINCT ...) >= 2`). Every person on such an issue has someone
  else to be connected to, and its project supports that connection. The roles may be
  the same or different, as the note says.
- The two `SELECT DISTINCT` parts joined by `UNION`: **step 5**, every person holding a
  role on a shared issue, as `person`, and every project of a shared issue, as
  `project`, each once, in one set (checklist item 5).

The Q11 adapter turns each row into `<kind>:<id>`. It adds and drops nothing.

## `Q11.sources.1.sql`

The known answer has one source step, with kinds `issue` and `time_entry`.

- The same `population`, `holds_role` and `shared` as the answer file: **step 1** to
  **step 4**.
- `LEFT JOIN model.logged_time ... AND t.seconds > 0`: every positive time entry on a
  shared issue, each of which establishes its author's logging role (**step 3**). On a
  shared issue that author always has someone else to be connected to. A shared issue
  with no positive entry keeps one row with a NULL `time_entry`, which under AC-12 as
  amended on 2026-11-12 is no ID; the issue still counts in the `issue` column.

## Checklist notes

No date bound applies (item 2). The one count is `count(DISTINCT ...)`, not a sum
(item 3). No group with a zero is listed (item 4). No path is built, so item 9 does not
apply. The only number is the two people a connection needs; no ID is written (item 10).
