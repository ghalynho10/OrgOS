# Q05 in SQL, clause by clause

Question: which people have logged hours on issues assigned to someone else, and how many
hours have they logged on those issues?

Both files read only schema `model` as the reader login: `model.logged_time` (one row per
time entry: its author in `person_key`, its issue in `issue_key`, its signed amount in
`seconds`, its changelog history ID in `history_id`) and `model.issue` (its project in
`project_key`, its current assignee in `assignee_key`, null when there is none).

## `Q05.answer.sql`

- `FROM model.logged_time AS t INNER JOIN model.issue AS i ON i.issue_key = t.issue_key`:
  each entry joins its one issue (`issue_key` is the key of `model.issue`), so the join
  repeats no entry and the sum counts each amount once (checklist item 5).
- `i.project_key IN (...)`: **step 1**, the seven project population, named as the reading
  note names it.
- `i.assignee_key IS NOT NULL AND i.assignee_key <> ''`: **step 2**, unassigned issues
  (missing, null or exactly `''`) are excluded (checklist item 6). The reading note also
  excludes issues assigned to a flagged bot; the flagged set is empty for this corpus
  (spec 0006 AC-17), so no clause is needed and none is written.
- `t.seconds > 0`: **step 3**, positive entries only (checklist item 7, spec 0006 AC-15).
  Time entry authors are never bots for the same reason as above.
- `t.person_key <> i.assignee_key`: **step 3**, the entry's author differs from the
  issue's current assignee.
- `sum(t.seconds) AS seconds` with `GROUP BY t.person_key`: **step 4**, the retained
  amounts summed per author, kept in seconds (the reading note divides by 3600 for display
  only). A `sum`, not a `count`: the answer is an amount. Only authors with a retained
  entry form a group, so no author gets a NULL or a 0 (checklist item 3 is about counts).
- `ORDER BY t.person_key`: for reading only; `compare` sorts a map itself.

The Q05 adapter turns each row into `person:<person_key>` with its `seconds`. It adds no
person, fills no zero and sums nothing.

## `Q05.sources.1.sql`

The known answer has one source step, with kinds `issue` and `time_entry`: every
contributing entry and its issue.

- `SELECT DISTINCT i.issue_key AS issue, t.history_id AS time_entry`: one row per
  contributing entry, a column per kind. An entry's ID is its changelog history ID, bare
  inside the step (spec 0005: `time_entry:<history id>`). The `issue` column repeats once
  per entry of the same issue; a step is read as a set of IDs per kind, so the repeat
  counts once. Every listed issue has at least one entry, so neither column holds a NULL.
- The `WHERE` holds the same conditions as the answer file: **step 1**, **step 2**,
  **step 3**. These are the entries **step 4** sums.

## The difference from the Cypher pair

None in meaning. SQL reads the assignee from the `assignee_key` column, where the graph
follows `ASSIGNED_TO`; an issue with no assignee has a null column in SQL and no
relationship in the graph. Both come from the same `model_int` edge table.
