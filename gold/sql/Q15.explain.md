# Q15 in SQL, clause by clause

Question: what is the total logged hours on CLOUD-643 and all of its sub-tasks combined?

Both files read `model.issue` (`issue_key`, `project_key`, `parent_key`) and
`model.logged_time` (one row per time entry: `history_id`, `issue_key`, signed
`seconds`). A child names its parent in `parent_key`.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 4,
Q15 has one source step in every case, listing `issue`, `parent` and `time_entry`, even if
the total is 0 or a list is empty; the earlier ruling, reading B for every parent hop, so
the step adds kind `parent` holding the direct child keys; and the accepted plan, the scope
is all of CLOUD, the parent and the sub-tasks are conditions inside it, and an entry with
no author counts in hours. The standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q15.answer.sql`

- The first `SELECT` of `family`, `WHERE p.issue_key = 'CLOUD-643' AND p.project_key =
  'CLOUD'`: **step 1**, the parent record in CLOUD. `CLOUD-643` is named in the question,
  so the literal check allows it.
- The second `SELECT` of `family`, `INNER JOIN model.issue AS p ON p.issue_key =
  c.parent_key`: **step 2**, every direct child by its own `parent_key`. One join is one
  hop, so a grandchild never counts. Issue links and shared people are not read.
- `UNION` puts the parent and its children in one list of keys, each once.
- `INNER JOIN model.logged_time AS t ON t.issue_key = f.issue_key AND t.seconds > 0`:
  **step 3**, the positive entries on the parent and the children (checklist item 7). Each
  entry has one `issue_key`, and each key is in `family` once, so no entry is counted
  twice (checklist item 5). No author clause: an entry with no author counts (the
  accepted plan), none exists in this corpus anyway (spec 0006 AC-16), and the flagged bot
  set is empty (spec 0006 AC-17).
- `coalesce(sum(t.seconds), 0) AS seconds`: **step 4**, the retained amounts summed, in
  seconds. The note says an issue with no qualifying entries contributes zero, so when no
  entry joins at all the total is 0, not NULL. This is a sum the question asks for, not a
  count, so checklist item 3 is met by the `coalesce`, written in the query and not the
  adapter (checklist item 4).

The Q15 adapter returns the one `seconds` value. It adds and drops nothing.

## `Q15.sources.1.sql`

The known answer has one source step, with kinds `issue`, `parent` and `time_entry`
(ruling 4).

- `family`'s first `SELECT`: **step 1**, the parent's own issue record in `issue`, with a
  NULL `parent` cell, which under AC-12 as amended on 2026-11-12 is no ID.
- `family`'s second `SELECT`: **step 2**, each sub-task's issue record in `issue` and its
  parent hop in `parent` (the child key, reading B).
- `LEFT JOIN model.logged_time AS t ON ... AND t.seconds > 0`: **step 3**, every positive
  entry on the parent or a child, the entries whose amounts **step 4** sums. The condition
  sits in the join, so an issue with no positive entry keeps one row with a NULL
  `time_entry`, and if none has one the kind still comes back as `[]` (checklist item 11,
  ruling 4).
- `SELECT DISTINCT`: one row per issue and entry.

## Checklist notes

No date bound applies (item 2). The answer sums, the `coalesce` gives 0 for nothing found
(item 3). Missing, null and `""` do not arise: no key here can be empty, and `model` holds
no empty string in a used column (spec 0006 AC-26). No path is built, so item 9 does not
apply. No number is written; the one ID is the key the question names (item 10). Q15 is
not zero guarded, so it has no stage files (item 13).

## The difference from the Cypher pair

None in meaning. The graph reads the parent hop as a `HAS_PARENT` relationship from child
to parent and the entries as `LOGGED_TIME` relationships; its `OPTIONAL MATCH` keeps an
issue with no entry as SQL's outer join does, and its `sum` over no match is also wrapped
in `coalesce`.
