# Q09 in SQL, clause by clause

Question: which chains of related issues show work passing between different assignees,
and what are the people, issues, projects, and relationship types in each chain?

The file reads `model.issue` (`issue_key`, `project_key`, `assignee_key`, NULL when
missing) and `model.issue_link` (`link_id`, `from_issue_key`, `to_issue_key`), where a
row reads "from_issue_key outward_label to_issue_key" (checklist item 8).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`:
ruling 1, a complete one hop chain counts (`hops = 2` is metadata and sets no minimum);
ruling 2, each hop's step lists `issue_link` plus both issues of that hop, and several
links between the same two issues stay one path with all their link IDs in that hop;
ruling 3, each chain is stored in both directions, as two paths.

## The answer layout

A path answer (spec 0011 AC-12, amended 2026-11-12): one row per chain and direction, a
`path` column with the issue keys in order, and one list column per kind with one item
per hop: `issue_link` holds each hop's link IDs, `issue` each hop's two issue keys. There
is no sources file. The Q09 adapter adds the `issue:` prefix to each path key and turns
each row into one step per hop; it sorts, filters and fills nothing.

The note also asks to report each issue's project and assignee and each hop's label in
the traversal direction. Those are display values, not source kinds: the known answer's
hops list `issue` and `issue_link` only, and the adapter refuses a column that is not a
kind (AC-12). They are left out of the file, and anyone can read them from the issue and
link records the steps cite.

## `Q09.answer.sql`

- `assigned`: **step 1**, the issues of the seven projects whose `assignee_key` is not
  NULL and not `""` (checklist item 6). The flagged bot set is empty for this corpus
  (spec 0006 AC-17), so no bot clause is written.
- `link`: **step 2**, links of any type whose two ends are both in `assigned` and have
  different assignee keys. A link from an issue to itself has equal keys, so it drops
  here.
- `hop`: **step 3**, "follow links in either direction". Each qualifying link gives one
  hop from its outward side and one from its inward side. `GROUP BY` the two ends makes
  several links between the same two issues one hop, in either direction, with every
  link ID in `jsonb_agg` (ruling 2).
- `walk`: **step 3**, simple paths over those hops. The first part takes each hop as a
  one hop path; the recursive part adds one hop from the last issue of the path.
- `cardinality(w.path) < 6`: a path grows only while it has fewer than six issues, so it
  stops at five hops, the question's `max_hops` (checklist item 9).
- The two `NOT EXISTS` tests: **step 4**, complete chains only. A path is refused when a
  qualifying hop joins its first issue, or its last issue, to an issue not on the path.
  A one hop path passes both when nothing extends it (ruling 1).

## How each chain comes back in both directions

`hop` holds every qualifying link both ways, so the walk builds each chain from either
end, and step 4 treats the two ends the same way. A complete chain read from `A` to `E`
and the same chain read from `E` to `A` are both complete, so both are rows: two paths,
as ruling 3 asks. Nothing removes one of them.

## How a repeated issue is forbidden

`NOT h.dst = ANY(w.path)` in the recursive part: a hop is added only when its target is
not already on the path, and a one hop path never has equal ends, because a self link
drops in `link`. Following links in both directions means every hop has a hop straight
back, and this test is what stops a path from returning over it. The same `ANY(w.path)`
test in step 4 means an extension back onto the path does not count, as the note's
"without repeating an issue" says.

## How a chain past hop 5 is detected

The walk stops at five hops, but step 4's second test looks one hop further: for a five
hop path it asks whether a qualifying hop joins the last issue to an issue not on the
path. If one does, the five hop path is a section of a longer chain and is left out,
which is what "a five-hop chain qualifies only if it cannot be extended" and "exclude
partial sections of longer chains" ask (checklist item 9). The first test does the same
at the start. A chain longer than five hops therefore returns nothing, never a five hop
piece of it.

## Checklist notes

No date bound applies (item 2), nothing is counted or summed (items 3, 7), no group is
listed (item 4). `GROUP BY` the two ends removes repeated hops (item 5). Direction is
ignored on purpose, as the note says, and every link type counts, so no label family is
chosen (item 8). The only numbers are the cap, read from `max_hops`, and array
positions; no ID is written (item 10).

## The difference from the Cypher pair

None in meaning. SQL builds the two way hop list first, merging several links into one
hop, and then walks it; the graph matches undirected paths over the 17 link types and
merges paths with the same issues afterwards. A missing assignee is NULL here and no
`ASSIGNED_TO` relationship in the graph.
