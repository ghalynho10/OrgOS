# Q16 in SQL, clause by clause

Question: how many open Highest priority bugs are blocked by, or depend on, at least one
unresolved issue?

The files read `model.issue` (`issue_key`, `project_key`, `issue_type_name`,
`priority_name`, `resolution_name`) and `model.issue_link` (one row per link: `link_id`,
`from_issue_key` on the outward side, `to_issue_key` on the inward side, `outward_label`,
`inward_label`).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: the
accepted plan, the scope is the seven projects with the other conditions inside it, and
Q16's count of 0 has the empty step list. Commit `b13f405`, ruling 5: a count of 0 has
sources `[]`. So the known answer has no source step and this pair has no sources file
(spec 0011 AC-11). Q16 is zero guarded (AC-18), so it has one stage file per numbered
source step of the reading note.

## How a link's direction reads in `model.issue_link`

A link row runs from its outward side (`from_issue_key`) to its inward side
(`to_issue_key`): "from `outward_label` to". Checklist item 8.

- The note's first connection is `type.inward` equal to "is blocked by", on the bug, with
  the other issue in `inwardIssue`. Read from the bug, the bug "is blocked by" the other
  issue, so the other issue "blocks" the bug: the other issue is the outward side and the
  bug the inward side. Here that is `inward_label = 'is blocked by'` with the bug in
  `to_issue_key` and the other issue in `from_issue_key`.
- The second is `type.outward` equal to "depends on", on the bug, with the other issue in
  `outwardIssue`: the bug "depends on" the other issue, so the bug is the outward side.
  Here that is `outward_label = 'depends on'` with the bug in `from_issue_key` and the
  other issue in `to_issue_key`.

The store holds these two label texts as written: link type `Blocker` has `blocks` and
`is blocked by`, and `Depends` has `depends on` and `depended on by`. No other direction or
label is followed.

## `Q16.answer.sql`

- `bug`: **step 1**. `project_key IN (...)` is the seven project population. `issue_type_name
  = 'Bug'` and `priority_name = 'Highest'` are the current type and priority.
  `(resolution_name IS NULL OR resolution_name = '')` is open: missing (NULL in `model`,
  including a missing containing object) or exactly `""` (checklist item 6). No status
  condition.
- `connection`: **step 2**, the two labels in their directions above, each a join from
  the bug to the link on the bug's own side. `UNION ALL` keeps every link with its bug and
  other end; the count below is `DISTINCT`, so a repeat cannot add a bug.
- `INNER JOIN model.issue AS o ON o.issue_key = c.other_key WHERE o.project_key IN (...)
  AND (o.resolution_name IS NULL OR o.resolution_name = '')`: **step 3**, the other end is
  a corpus issue and unresolved, the same missing, null or `""` rule.
- `count(DISTINCT c.bug_key) AS issues`: **step 4**, each qualifying bug once, however
  many qualifying links or linked issues it has (checklist items 3 and 5). With no match
  `count` gives 0, never NULL.

The Q16 adapter returns the one `issues` value and the empty step list as the files give
it. It adds and drops nothing.

## The stage files (the zero guard, checklist item 13)

Each returns one integer, the store's own count after the conditions of **step 1** up to
**step n**, added in the order of the reading note, none added, dropped or merged. Each
stage counts the records its step names.

- Stage 1, `issues`: **step 1** only, the open Highest priority corpus bugs. It must be
  above 0, so the population a zero is counted over exists.
- Stage 2, `links`: adds **step 2**, the distinct links on those bugs with the specified
  label and direction, counted by `link_id`.
- Stage 3, `links`: adds **step 3**, those links whose other end is an unresolved corpus
  issue.
- Stage 4, `issues`: **step 4**, the distinct bugs on the stage 3 links. It holds the same
  conditions as the answer file and equals it by construction.

The guard accepts the pair only when these four counts equal the graph's four.

## The difference from the Cypher pair

None in meaning. The graph stores each link as a relationship from its outward side to
its inward side with `outwardLabel` and `inwardLabel`, so "is blocked by" is a
relationship ending at the bug and "depends on" one starting at it. SQL reads the project
from `project_key`; the graph follows `IN_PROJECT`. A missing resolution is NULL here and
an absent property there, and `IS NULL OR = ''` treats both the same way.
