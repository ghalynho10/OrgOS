# Q17 in SQL, clause by clause

Question: which people logged hours on issues in different projects that are linked to
each other, and which projects, issues, and hours connect them?

The files read `model.issue` (`issue_key`, `project_key`), `model.issue_link` (one row
per link: `link_id`, `from_issue_key`, `to_issue_key`) and `model.logged_time` (one row
per time entry: `history_id`, `person_key`, `issue_key`, signed `seconds`).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 1,
Q17 has two source steps in this order, `issue` and `issue_link`, then `person` and
`time_entry`; the person list holds returned people only, and the entries are theirs on
qualifying issues. The correction in the same commit body: where a note names a shared
person as the connection, that hop's step lists `person`. The accepted plan: the scope is
the seven projects, with the other conditions inside it. The standing sources rule is in
commits `2ecf29c` and `b13f405`: project keys shown on issues are display values, not a
kind, so no step lists `project`.

## `Q17.answer.sql`

- `corpus`: the population, issues whose current `project_key` is one of the seven.
- `cross_link`: **step 1**, directly linked corpus issues in different projects. Both
  ends join `corpus`, so both are corpus issues, and `a.project_key <> b.project_key`
  keeps only links across projects. No label or type condition: any link type
  qualifies. Direction is ignored: each link is one row with its two ends, and which end
  sits in `a_key` does not change any result below, since both ends are treated alike.
  A parent relation is not in `model.issue_link`, so it never counts, and one join is one
  link, so no chain counts.
- `entry`: the positive entries on corpus issues (checklist item 7). The flagged bot set
  is empty (spec 0006 AC-17) and every entry has an author (spec 0006 AC-16), so no bot
  or author clause is written.
- `logger`: each (person, issue) with at least one positive entry, once.
- `pair`: **step 2**, a link whose two ends both have a positive entry by the same
  author, matched on `person_key`. One row per link and qualifying author.
- `person_issue`: **step 3**, per author, the distinct issues sitting in at least one of
  their qualifying pairs. `UNION` (not `UNION ALL`) keeps each (person, issue) once,
  however many pairs it sits in (checklist item 5).
- The final `SELECT ... sum(e.seconds) ... GROUP BY pi.person_key`: **step 4**, each
  author's positive entries on those issues summed once each. An entry joins its one
  (person, issue) row, so an entry on an issue in several pairs is still counted once.
  Every returned person has at least one entry, so `sum` is never NULL here.

The Q17 adapter turns each row into `(person:<person_key>, seconds)`. It adds and drops
nothing.

## `Q17.sources.1.sql`

The first known source step, the issue link hop, kinds `issue` and `issue_link`. Same
`corpus`, `cross_link`, `logger` and `pair` as the answer (**step 1** and **step 2**).
`pair` here keeps each link and its two ends once, whoever the author is. The final
`UNION` returns both ends of each qualifying pair, each with its supporting link, so
every issue and link of a returned person's qualifying pairs is listed. A pair qualifies
only through a person, and every such person is returned, since a `map` answer lists
every qualifying person.

## `Q17.sources.2.sql`

The second known source step, the shared person hop, kinds `person` and `time_entry`
(ruling 1 and the correction). The same chain as the answer through **step 3**, then
every contributing entry of each returned person on their qualifying issues, the entries
**step 4** sums. `SELECT DISTINCT` lists each entry once. No NULL cell can arise: every
row has a person and an entry.

## Checklist notes

No date bound applies (item 2). Item 3: the answer sums seconds, which the question asks
for, and no group is empty. Item 4: a person with no qualifying pair is not a member of
the answer, so no zero rows are owed. Item 6 does not arise: no key used here can be
missing or empty (spec 0006 AC-26). No path is built (item 9). No number or ID is written
beyond the seven project keys of the reading note (item 10).

## The difference from the Cypher pair

None in meaning. The graph holds each link as one relationship carrying `linkId`, read
once from its start node to its end node, where SQL reads one `issue_link` row with
`from_issue_key` and `to_issue_key`. SQL reads the project from `project_key`; the graph
follows `IN_PROJECT`. SQL keeps each (person, issue) once with `UNION`; the graph with
`WITH DISTINCT p, i`.
