# Q10 in Cypher, clause by clause

Question: which people have worked on issues that block, depend on, duplicate, or
supersede issues assigned to other people, and which people are connected through those
relationships?

Both files read the read only `neo4j` database: `Issue` nodes (`issueKey`), their one
`IN_PROJECT` relationship to a `Project`, their `ASSIGNED_TO` relationship to a `Person`
(`personKey`), absent when the issue has no assignee, and the link relationships, which
run from the outward side to the inward side and carry `linkId`, `outwardLabel` and
`inwardLabel`.

## The ruling this pair follows

Your ruling of 2026-11-02, recorded in the body of main repo commit `1d793bd`, ruling 4:
Q10 reading B, a flat list of people is the answer, and the step lists `issue`,
`issue_link` and `person`, with the qualifying source and target assignees.

## Which end is the source (checklist item 8)

A link relationship reads "start outwardLabel end", and from the other end "end
inwardLabel start".

- An outward label `blocks`, `depends on` or `duplicates`: the reading note takes it on
  the source issue with the target in `outwardIssue`, so the source is the start node
  and the target the end node.
- The inward label `supersedes`: the note takes it on the source issue with the target
  in `inwardIssue`. In Jira, a link entry on issue A with `inwardIssue` B and inward label
  `supersedes` reads "A supersedes B", and the graph stores that link from B, the outward
  side, to A. So the source is the end node and the target the start node.

Labels are matched exactly, never the relationship type, and only these four in only
these directions: an inward `blocks` or an outward `supersedes` does not count. A
`HAS_PARENT` relationship has no label, so it never matches.

## `Q10.answer.cypher`

- `CALL () { MATCH (s:Issue)-[r]->(t:Issue) WHERE r.outwardLabel IN [...] RETURN s, r, t
  UNION MATCH (t:Issue)-[r]->(s:Issue) WHERE r.inwardLabel = 'supersedes' RETURN s, r,
  t }`: **step 2**, the qualifying links with `s` the source and `t` the target, as read
  above.
- `MATCH (s)-[:IN_PROJECT]->(ps:Project), (t)-[:IN_PROJECT]->(pt:Project),
  (s)-[:ASSIGNED_TO]->(a:Person), (t)-[:ASSIGNED_TO]->(b:Person)` with both project keys
  in the seven: **step 1** on both ends, each in the population with an assignee
  (checklist item 6). The flagged bot set is empty for this corpus (spec 0006 AC-17), so
  no bot clause is written.
- `a.personKey <> b.personKey`: **step 3**, the two assignee keys differ. A link from an
  issue to itself has one assignee, so it drops.
- `RETURN DISTINCT a.personKey AS person_key`: **step 4**, the distinct source assignees
  (checklist item 5). A target assignee is in the answer only when that person is also a
  source assignee somewhere, as the note says.

The Q10 adapter turns each row into `person:<person_key>`. It adds and drops nothing.

## `Q10.sources.1.cypher`

The known answer has one source step, with kinds `issue`, `issue_link` and `person`.

- The same `CALL` and `MATCH` as the answer file: **step 1** to **step 3**.
- `UNWIND [[s.issueKey, a.personKey], [t.issueKey, b.personKey]] AS side RETURN DISTINCT
  side[0] AS issue, r.linkId AS issue_link, side[1] AS person`: one row per end of each
  qualifying relationship, with that end's issue, the link and that end's assignee. So
  every source and target issue, every qualifying link, and both the source and the
  target assignees are in the step (ruling 4). These are the relationships whose source
  assignees **step 4** returns.

## The difference from the SQL pair

None in meaning. SQL reads each link as a row from its outward side to its inward side,
the same direction as a relationship here, and reads the source from the label in the
same way. A missing assignee is no `ASSIGNED_TO` relationship here and NULL in SQL.
