# Q12 in Cypher, clause by clause

Question: in CLOUD and CLOV, which parent issues have sub-tasks assigned to multiple
people, and who are those people?

Both files read the read only `neo4j` database: `Issue` nodes (`issueKey`), their one
`IN_PROJECT` relationship to a `Project`, the `HAS_PARENT` relationship from a child
`Issue` to its parent, and the `ASSIGNED_TO` relationship to a `Person` (`personKey`),
absent when the issue has no assignee.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`: ruling
4, Q12 reading B, the step lists `issue`, `parent` and `person`; ruling 5, a parent hop
adds the kind `parent` holding the direct child keys. The scope is CLOUD and CLOV.

## `Q12.answer.cypher`

- `MATCH (c:Issue)-[:HAS_PARENT]->(p:Issue)`: **step 2**, each direct sub-task with its
  parent. The pattern is one relationship, so a grandchild never reaches its
  grandparent.
- `MATCH (p)-[:IN_PROJECT]->(pp:Project) WHERE pp.projectKey IN ['CLOUD', 'CLOV']`:
  **step 1**, parents in the two projects.
- `MATCH (c)-[:IN_PROJECT]->(pc:Project), (c)-[:ASSIGNED_TO]->(a:Person) WHERE
  pc.projectKey IN [...]`: **step 3**, sub-tasks in the two projects with an assignee; a
  missing key has no relationship (checklist item 6). The flagged bot set is empty for
  this corpus (spec 0006 AC-17), so no bot clause is written.
- `WITH p, collect(DISTINCT a.personKey) AS people`: **step 4**, the distinct assignee
  keys per parent (checklist item 5).
- `WHERE size(people) >= 2 RETURN p.issueKey AS issue_key`: **step 5**, the parents with
  at least two, each once, as the grouping is by `p`.

The Q12 adapter turns each row into `issue:<issue_key>`. It adds and drops nothing.

## `Q12.sources.1.cypher`

The known answer has one source step, with kinds `issue`, `parent` and `person`.

- The same matches as the answer file: **step 1** to **step 3**; the `WITH` also keeps
  every contributing sub-task with its assignee, and `size(people) >= 2` is **step 4**
  and **step 5**.
- `UNWIND [{issue: p.issueKey, parent: null, person: null}] + [k IN children | ...]`:
  first each qualifying parent's own issue record, in `issue`, with null `parent` and
  `person` cells, which under AC-12 as amended on 2026-11-12 are no ID; then every
  contributing sub-task, its issue record in `issue`, its parent hop in `parent` (the
  child key, ruling 5), and its assignee in `person`. So every qualifying assignee is in
  the step, as the note asks.

## Checklist notes

No date bound applies (item 2). Nothing is summed (item 3). No group with a zero is
listed (item 4). No path is built, so item 9 does not apply. The only number is the two
assignees the question asks for; no ID is written (item 10).

## The difference from the SQL pair

None in meaning. SQL reads the parent hop as the child's `parent_key` column, and a
missing assignee as NULL where the graph has no `ASSIGNED_TO` relationship.
