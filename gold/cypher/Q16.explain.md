# Q16 in Cypher, clause by clause

Question: how many open Highest priority bugs are blocked by, or depend on, at least one
unresolved issue?

The files read `Issue` nodes (`issueTypeName`, `priorityName`, `resolutionName`), the
`IN_PROJECT` relationship to `Project` (`projectKey`), and the issue link relationships,
one per link, each running from its outward side to its inward side with `linkId`,
`outwardLabel` and `inwardLabel`.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: the
accepted plan, the scope is the seven projects with the other conditions inside it, and
Q16's count of 0 has the empty step list. Commit `b13f405`, ruling 5: a count of 0 has
sources `[]`. So the known answer has no source step and this pair has no sources file
(spec 0011 AC-11). Q16 is zero guarded (AC-18), so it has one stage file per numbered
source step of the reading note.

## How a link's direction reads in the graph

A link relationship runs from its outward side to its inward side: "start
`outwardLabel` end". Checklist item 8.

- The note's first connection is `type.inward` equal to "is blocked by", on the bug, with
  the other issue in `inwardIssue`: the bug "is blocked by" the other issue, so the other
  issue "blocks" the bug and is the start node. `MATCH (o:Issue)-[l]->(b) WHERE
  l.inwardLabel = 'is blocked by'`.
- The second is `type.outward` equal to "depends on", on the bug, with the other issue in
  `outwardIssue`: the bug "depends on" the other issue, so the bug is the start node.
  `MATCH (b)-[l]->(o:Issue) WHERE l.outwardLabel = 'depends on'`.

The relationship type is left open and the label is matched instead, as the note names
labels, not types. `HAS_PARENT` also joins two issues but has no label property, so it
never matches; `IN_PROJECT` ends at a `Project`, not an `Issue`.

## `Q16.answer.cypher`

- The first `MATCH ... WHERE`: **step 1**. `bp.projectKey IN [...]` is the seven project
  population. `issueTypeName = 'Bug'` and `priorityName = 'Highest'` are the current type
  and priority. `(b.resolutionName IS NULL OR b.resolutionName = '')` is open: a missing
  value is an absent property in the graph, read as null, or exactly `""` (checklist item
  6). No status condition.
- `CALL (b) { ... UNION ... }`: **step 2**, the two labels in their directions above,
  returning each link with its other end.
- `MATCH (o)-[:IN_PROJECT]->(op:Project) WHERE op.projectKey IN [...] AND
  (o.resolutionName IS NULL OR o.resolutionName = '')`: **step 3**, the other end is a
  corpus issue and unresolved.
- `RETURN count(DISTINCT b) AS issues`: **step 4**, each qualifying bug once, however many
  qualifying links or linked issues it has (checklist items 3 and 5). With no match the
  aggregate still returns one row, 0.

The Q16 adapter returns the one `issues` value and the empty step list as the files give
it. It adds and drops nothing.

## The stage files (the zero guard, checklist item 13)

Each returns one integer, the store's own count after the conditions of **step 1** up to
**step n**, added in the order of the reading note, none added, dropped or merged. Each
stage counts the records its step names.

- Stage 1, `issues`: **step 1** only, the open Highest priority corpus bugs. It must be
  above 0.
- Stage 2, `links`: adds **step 2**, the distinct links on those bugs with the specified
  label and direction, counted by `linkId`.
- Stage 3, `links`: adds **step 3**, those links whose other end is an unresolved corpus
  issue.
- Stage 4, `issues`: **step 4**, the distinct bugs on the stage 3 links. It holds the same
  conditions as the answer file and equals it by construction.

The guard accepts the pair only when these four counts equal the SQL four.

## The difference from the SQL pair

None in meaning. SQL holds the outward side in `from_issue_key` and the inward side in
`to_issue_key`; the graph holds them as the start and end node. SQL reads the project
from `project_key`; the graph follows `IN_PROJECT`.
