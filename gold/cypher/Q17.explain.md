# Q17 in Cypher, clause by clause

Question: which people logged hours on issues in different projects that are linked to
each other, and which projects, issues, and hours connect them?

The files read `Issue` nodes (`issueKey`), the `IN_PROJECT` relationship to `Project`
(`projectKey`), the issue link relationships (17 types, one relationship per link, each
carrying `linkId`) and the `LOGGED_TIME` relationship from a `Person` (`personKey`) to an
`Issue` (`historyId`, signed `seconds`).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 1,
Q17 has two source steps in this order, `issue` and `issue_link`, then `person` and
`time_entry`; the person list holds returned people only, and the entries are theirs on
qualifying issues. The correction in the same commit body: where a note names a shared
person as the connection, that hop's step lists `person`. The accepted plan: the scope is
the seven projects, with the other conditions inside it. The standing sources rule is in
commits `2ecf29c` and `b13f405`: project keys shown on issues are display values, not a
kind, so no step lists `project`.

## `Q17.answer.cypher`

- `MATCH (a:Issue)-[l]->(b:Issue) WHERE l.linkId IS NOT NULL`: **step 1**, a direct
  issue link of any type. Only the 17 link types carry `linkId`; `HAS_PARENT` also joins
  two issues but has none, so a parent relation never counts. The pattern is directed so
  each link is read once; direction is otherwise ignored, since both ends are treated
  alike below. One relationship is one link, so no chain counts.
- `MATCH (a)-[:IN_PROJECT]->(pa:Project), (b)-[:IN_PROJECT]->(pb:Project) WHERE ...`: both
  ends in the seven projects, and `pa.projectKey <> pb.projectKey`, different projects.
- `MATCH (p:Person)-[ta:LOGGED_TIME]->(a), (p)-[tb:LOGGED_TIME]->(b) WHERE ta.seconds > 0
  AND tb.seconds > 0`: **step 2**, the same author has a positive entry on each end
  (checklist item 7). The flagged bot set is empty (spec 0006 AC-17).
- `WITH DISTINCT p, a, b`: one row per qualifying pair and author, however many entries
  matched.
- `UNWIND [a, b] AS i WITH DISTINCT p, i`: **step 3**, per author, the distinct issues in
  at least one of their qualifying pairs, each once however many pairs it sits in
  (checklist item 5).
- `MATCH (p)-[t:LOGGED_TIME]->(i) WHERE t.seconds > 0 RETURN p.personKey AS person_key,
  sum(t.seconds) AS seconds`: **step 4**, each author's positive entries on those issues,
  each entry once, since each (person, issue) is one row.

The Q17 adapter turns each row into `(person:<person_key>, seconds)`. It adds and drops
nothing.

## `Q17.sources.1.cypher`

The first known source step, the issue link hop, kinds `issue` and `issue_link`. The
same **step 1** and **step 2** matches as the answer, then `WITH DISTINCT l, a, b` keeps
each qualifying link and its two ends once, whoever the author is, and `UNWIND [a, b]`
returns both ends with the supporting link's `linkId`. A pair qualifies only through a
person, and every such person is returned, since a `map` answer lists every qualifying
person.

## `Q17.sources.2.cypher`

The second known source step, the shared person hop, kinds `person` and `time_entry`
(ruling 1 and the correction). The same chain as the answer through **step 3**, then
every contributing entry of each returned person on their qualifying issues, the entries
**step 4** sums, each once with `RETURN DISTINCT`.

## Checklist notes

No date bound applies (item 2). Item 3: the answer sums seconds, which the question asks
for, and no group is empty. Item 4: a person with no qualifying pair is not a member of
the answer, so no zero rows are owed. Item 6 does not arise: a missing property is absent
in the graph and no key used here can be empty. No path is built (item 9). No number or
ID is written beyond the seven project keys of the reading note (item 10).

## The difference from the SQL pair

None in meaning. SQL reads each link as one `issue_link` row with `from_issue_key` and
`to_issue_key`; the graph reads one relationship from its start node to its end node.
SQL keeps each (person, issue) once with `UNION`; the graph with `WITH DISTINCT p, i`.
