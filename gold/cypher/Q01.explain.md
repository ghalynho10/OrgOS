# Q01 in Cypher, clause by clause

Question: for each of the seven projects, how many issues created between January 1 and
March 31, 2013 (UTC) are still unresolved and have no assignee?

Both files read the `neo4j` database while it is read only: `Project` nodes (key
`projectKey`), `Issue` nodes (key `issueKey`), each issue linked to its project by
`IN_PROJECT` and to its assignee, when it has one, by `ASSIGNED_TO`.

## `Q01.answer.cypher`

- `MATCH (p:Project) WHERE p.projectKey IN [...]`: **step 1**, the seven project
  population, named exactly as the reading note names them. Each row of the result
  starts from a project, so a project is listed even when none of its issues qualifies.
- `OPTIONAL MATCH (i:Issue)-[:IN_PROJECT]->(p) WHERE ...`: the graph's outer join. The
  `WHERE` right after an `OPTIONAL MATCH` belongs to it, so it filters which issues
  match and never removes the project: a project with no qualifying issue keeps one row
  with `i` null (checklist item 4).
- `i.createdAt >= datetime('2013-01-01T00:00:00Z') AND i.createdAt <
  datetime('2013-04-01T00:00:00Z')`: **step 2**, the half open interval `[start, end)`.
  The start is included, the end excluded. Both bounds are in the `Z` form, so they are
  UTC, the form every stored `datetime` has (spec 0008 AC-17, checklist item 2).
- `(i.resolutionName IS NULL OR i.resolutionName = '')`: **step 3**, still unresolved.
  Neo4j stores no null property, so a missing resolution reads as `IS NULL`; `= ''`
  covers the empty name (checklist item 6).
- `NOT EXISTS { (i)-[:ASSIGNED_TO]->(:Person) }`: **step 4**, no assignee. The graph
  holds an assignee as a relationship, not a property, so "missing, null or exactly ''"
  becomes "no `ASSIGNED_TO` relationship". A null assignee in `model_int` makes no
  relationship (spec 0006 AC-8).
- `count(DISTINCT i) AS issues`: **step 5**, the count per project. Cypher groups by the
  other value in `RETURN`, `p.projectKey`. `count` skips the null `i` of a project with
  no match, so it gives 0 (checklist item 3). `DISTINCT` counts each issue once
  (checklist item 5).
- `ORDER BY project_key`: for reading only; `compare` sorts a map itself.

The same Q01 adapter as SQL turns each row into `project:<project_key>` with its count.

## `Q01.sources.1.cypher`

- `MATCH (i:Issue)-[:IN_PROJECT]->(p:Project)` with the same four conditions: **step 1**
  (the seven projects), **step 2** (the UTC interval), **step 3** (unresolved),
  **step 4** (no assignee). These are the issue records **step 5** counts.
- `RETURN DISTINCT i.issueKey AS issue`: one column named after the kind, one issue key
  per row, so an empty result still names its kind and the step is kept as `issue: []`.

## The difference from the SQL pair

None in meaning. The assignee is a relationship here and a column in SQL, and the date
bounds use the `Z` form here and a `+00` offset in SQL. Both read the same load.
