# Q09 in Cypher, clause by clause

Question: which chains of related issues show work passing between different assignees,
and what are the people, issues, projects, and relationship types in each chain?

The file reads the read only `neo4j` database: `Issue` nodes (`issueKey`), their one
`IN_PROJECT` relationship to a `Project`, their `ASSIGNED_TO` relationship to a `Person`
(`personKey`), absent when the issue has no assignee, and the link relationships of the
17 link types, which run from the outward side to the inward side and carry `linkId`
(checklist item 8).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`:
ruling 1, a complete one hop chain counts (`hops = 2` is metadata and sets no minimum);
ruling 2, each hop's step lists `issue_link` plus both issues of that hop, and several
links between the same two issues stay one path with all their link IDs in that hop;
ruling 3, each chain is stored in both directions, as two paths.

## The answer layout

A path answer (spec 0011 AC-12, amended 2026-11-12): one row per chain and direction, a
`path` column with the issue keys in order, and one list column per kind with one item
per hop: `issue_link` holds each hop's link IDs, `issue` each hop's two issue keys. There
is no sources file. The Q09 adapter adds the `issue:` prefix to each path key and turns
each row into one step per hop; it sorts, filters and fills nothing.

The note also asks to report each issue's project and assignee and each hop's label in
the traversal direction. Those are display values, not source kinds: the known answer's
hops list `issue` and `issue_link` only, and the adapter refuses a column that is not a
kind (AC-12). They are left out of the file, and anyone can read them from the issue and
link records the steps cite.

## `Q09.answer.cypher`

- `MATCH p = (a:Issue) ((x:Issue)-[r:BLOCKER|...|SUPERSESSION]-(y:Issue) WHERE ...){1,5}
  (b:Issue)`: **step 3**, paths over any of the 17 link types, with no arrow, so a link
  is followed in either direction, one to five hops, the question's `max_hops`
  (checklist item 9). Naming the 17 types keeps `HAS_PARENT`, the other relationship
  between two issues, out, as the note says parent relations do not count.
- The `WHERE` inside the repeated part, checked on every hop while the path grows:
  **step 1**, both ends are in one of the seven projects and have an assignee (the
  `COLLECT` of their `personKey` is not empty; checklist item 6), and **step 2**, the two
  assignee keys differ. A self link has equal keys, so it drops here. The flagged bot set
  is empty for this corpus (spec 0006 AC-17), so no bot clause is written.
- `all(k IN range(0, size(r)) WHERE NOT nodes(p)[k] IN nodes(p)[k + 1..])`: no issue
  repeats (below).
- The two `NOT EXISTS { MATCH ... }` tests: **step 4**, complete chains only. A path is
  refused when a link of the 17 types, in either direction, joins its first issue, or
  its last issue, to an issue not on the path that is in the seven projects, has an
  assignee, and has a different one. A one hop path passes both when nothing extends it
  (ruling 1).
- `WITH [n IN nodes(p) | n.issueKey] AS path, r` then `UNWIND`, `collect(DISTINCT
  r[h].linkId)` grouped by `path` and `h`: several links between the same two issues, in
  either direction, match as several paths over the same issues. They are one chain, and
  each hop keeps every link ID (ruling 2, checklist item 5).
- `RETURN path, [...] AS issue_link, [...] AS issue`: each hop's link IDs, looked up by
  hop number, and its two issues, in path order.

## How each chain comes back in both directions

The pattern has no arrow, so it matches each chain from either end, and step 4 treats
the two ends the same way. A complete chain read from `A` to `E` and the same chain read
from `E` to `A` are both matched and both complete, so both are rows: two paths, as
ruling 3 asks. The grouping is by the ordered list of keys, so it never merges the two.

## How a repeated issue is forbidden

Cypher's default match mode forbids a repeated relationship in a path, not a repeated
node. With links followed both ways, a path could otherwise go around a loop of links
and come back to an issue. The query states it outright:
`all(k IN range(0, size(r)) WHERE NOT nodes(p)[k] IN nodes(p)[k + 1..])` keeps a path
only when no issue appears again later in it. It does not rely on the `ACYCLIC` path mode
of Cypher 25 (spec 0008 Follow-up), because an explicit test reads the same on any
version. In step 4, `NOT u IN nodes(p)` and `NOT w IN nodes(p)` mean an extension back
onto the path does not count, as the note's "without repeating an issue" says.

## How a chain past hop 5 is detected

The pattern stops at five hops, but step 4's second test looks one hop further: for a
five hop path it asks whether a qualifying link joins the last issue to an issue not on
the path. If one does, the five hop path is a section of a longer chain and is left out,
which is what "a five-hop chain qualifies only if it cannot be extended" and "exclude
partial sections of longer chains" ask (checklist item 9). The first test does the same
at the start. A chain longer than five hops therefore returns nothing, never a five hop
piece of it.

## Checklist notes

No date bound applies (item 2), nothing is counted or summed (items 3, 7), no group is
listed (item 4). Direction is ignored on purpose, as the note says, and every link type
counts, so no label family is chosen (item 8). The only numbers are the cap, read from
`max_hops`, and list positions; no ID is written (item 10).

## The difference from the SQL pair

None in meaning. SQL builds the two way hop list first, merging several links into one
hop, and then walks it; the graph matches undirected paths over the 17 link types and
merges paths with the same issues afterwards. A missing assignee is no `ASSIGNED_TO`
relationship here and NULL in SQL.
