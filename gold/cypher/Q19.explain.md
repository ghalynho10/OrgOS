# Q19 in Cypher, clause by clause

Question: which five projects have the most issues directly linked to issues in other
corpus projects?

Both files read `Issue` nodes (`issueKey`), the `IN_PROJECT` relationship to `Project`
(`projectKey`), and the issue link relationships (17 types, one relationship per link,
each carrying `linkId`).

## The rulings this pair follows

Your accepted plan of 2026-11-02, recorded in the body of main repo commit `25e339a`:
the scope is the seven projects, with the other conditions inside it, and Q19 is one
step: `project` holds only the returned projects, and `issue` holds the counted issues
plus the issues at the other end of their links, which may sit in a project that was not
returned. The reading note names the kinds `project`, `issue` and `issue_link`. The
standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q19.answer.cypher`

- `MATCH (a:Issue)-[l]->(b:Issue) WHERE l.linkId IS NOT NULL`: **step 2**, a direct link
  of any type. Only the 17 link types carry `linkId`; `HAS_PARENT` also joins two issues
  but has none, so a parent relation never counts. Each link is one relationship, so
  reading it once from start to end node deduplicates by link ID; one relationship is one
  link, so no chain counts.
- `MATCH (a)-[:IN_PROJECT]->(pa:Project), (b)-[:IN_PROJECT]->(pb:Project) WHERE ...`:
  **step 1**, both ends are corpus issues with their current project, and **step 2**,
  in different projects.
- `UNWIND [[pa, a], [pb, b]] AS side`: direction is ignored, so each end of each link is
  listed in its own project.
- `WITH pr, count(DISTINCT i) AS issues`: **step 3** and **step 4**, each issue once in
  its own project however many qualifying links, linked issues or partner projects it
  has (checklist items 3 and 5). Only a project with at least one qualifying issue forms
  a row.
- `ORDER BY issues DESC`, `collect`, `coalesce(ranked[4].issues, ranked[-1].issues) AS
  cutoff` and `WHERE r.issues >= cutoff`: **step 4** and **step 5**. The list is sorted
  highest first; the cutoff is the fifth count (index 4), or the lowest when fewer than
  five qualify; keeping every count at or above it keeps the top five and every project
  tied with the fifth. The `4` is the fifth place of the question's own five (checklist
  item 10).
- `RETURN ... ORDER BY issues DESC, project_key`: rank order, with ties in key order.

The Q19 adapter turns each row, in the query's order, into `(project:<project_key>,
issues)`. It adds and drops nothing.

## `Q19.sources.1.cypher`

The known answer has one source step, with kinds `project`, `issue` and `issue_link`.

- `CALL () { ... RETURN [...] AS returned }`: the returned projects, found exactly as the
  answer file finds them (**step 1** to **step 5**). Doing this first keeps the query
  inside the graph's transaction memory: an earlier draft collected every link end of
  every project before the cut and hit the 256 MiB limit before any try was run.
- The second `MATCH` reads every qualifying link again, and `UNWIND [[pa, a, b], [pb, b,
  a]]` lists each end with its project and the other end; `WHERE pr.projectKey IN
  returned` keeps only the counted issues of returned projects.
- `UNWIND [i, other] AS listed` with `RETURN DISTINCT pr.projectKey AS project,
  listed.issueKey AS issue, l.linkId AS issue_link`: the returned project, each counted
  issue, each qualifying link supporting it, and the issue at the other end. That issue
  may sit in a project that was not returned; that project is not listed (the accepted
  plan). The columns are read as sets.

## Checklist notes

No date bound applies (item 2). No hours (item 7). Item 4: a project with no qualifying
issue is outside the ranking by the note's own rule, so no zero row is owed. No path is
built (item 9).

## The difference from the SQL pair

None in meaning. SQL reads each link as one `issue_link` row keyed by `link_id` and
cuts with `rank() <= 5`; the graph reads one relationship per link and cuts at the fifth
count, the same set.
