# Q13 in Cypher, clause by clause

Question: for CLOV-108, list its sub-tasks with each one's assignee, status, and total
logged hours.

Both files read the read only `neo4j` database: `Issue` nodes (`issueKey`), their one
`IN_PROJECT` relationship to a `Project`, the `HAS_PARENT` relationship from a child
`Issue` to its parent, and the sources file also reads `LOGGED_TIME` relationships from
a `Person` to an `Issue` (signed `seconds`, `historyId`).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`: ruling
5, a parent hop adds the kind `parent` holding the direct child keys, and Q13 lists
`issue`, `parent` and `time_entry`; ruling 8, the registered scope is all of CLOV and the
rest are conditions inside it. The same commit body says Q13's answer holds the sub-task
IDs only; assignee, status and total hours are not stored. So the answer file returns
keys only, and assignee, status and hours are not computed here.

## `Q13.answer.cypher`

- `MATCH (p:Issue {issueKey: 'CLOV-108'})-[:IN_PROJECT]->(:Project {projectKey:
  'CLOV'})`: **step 1**, the parent record, CLOV-108 in CLOV. `CLOV-108` is named in the
  question, so the literal check allows it.
- `MATCH (c:Issue)-[:HAS_PARENT]->(p)`: **step 2**, every direct child. The pattern is
  one relationship, so a grandchild never counts.
- No filter on assignee, status or time: the note says to include sub-tasks with no
  assignee or no qualifying logged time. **Step 3** to **step 5** read display values
  only, which the answer does not store.
- `RETURN DISTINCT c.issueKey AS issue_key`: each sub-task once (checklist item 5).

The Q13 adapter turns each row into `issue:<issue_key>`. It adds and drops nothing.

## `Q13.sources.1.cypher`

The known answer has one source step, with kinds `issue`, `parent` and `time_entry`.

- The same parent match: **step 1**.
- `CALL (p) { RETURN p.issueKey AS issue, null AS parent, null AS time_entry UNION ...
  }`: first the parent's own issue record in `issue`, with null `parent` and
  `time_entry` cells, which under AC-12 as amended on 2026-11-12 are no ID.
- `MATCH (c:Issue)-[:HAS_PARENT]->(p)` in the second part: **step 2** and **step 3**,
  each sub-task's issue record in `issue` and its parent hop in `parent` (the child key,
  ruling 5).
- `OPTIONAL MATCH (:Person)-[t:LOGGED_TIME]->(c) WHERE t.seconds > 0`: **step 4**, every
  positive entry on a sub-task (checklist item 7), the entries whose amounts **step 5**
  sums. The `WHERE` sits inside the `OPTIONAL MATCH`, so a sub-task with no positive
  entry keeps one row with a null `time_entry`, and if no sub-task has one the kind
  still comes back as `[]` (checklist item 11). The flagged bot set is empty for this
  corpus (spec 0006 AC-17), so no bot clause is written.

## Checklist notes

No date bound applies (item 2). Nothing is counted or summed in the answer (item 3).
Every sub-task is a row whatever it holds (item 4). No path is built, so item 9 does not
apply. No number is written; the one ID is the key the question names (item 10).

## The difference from the SQL pair

None in meaning. SQL reads the parent hop as the child's `parent_key` column and time
entries as rows of `model.logged_time`; its outer join keeps a sub-task with no entry as
the `OPTIONAL MATCH` does here.
