# Q04 in Cypher, clause by clause

Question: for each project, how does the total time logged compare with the total original
estimates for its issues?

Both files read the read only `neo4j` database: `Project` nodes, `Issue` nodes (with
`timeOriginalEstimateS` in seconds, absent when missing) and their one `IN_PROJECT`
relationship, and `LOGGED_TIME` relationships from a `Person` to an `Issue` (signed
`seconds`, `historyId`).

## How the population is read

The reading note's population is the issues in the seven projects "with either logged time
or an original estimate". The query reads "logged time" by the note's own definition, at
least one positive entry, and "an original estimate" as an estimate that is present, so an
estimate of 0 counts and that issue is one of the "issues contributing zero" step 1 lists.
The answer value does not depend on this reading: an issue with no estimate and no
positive entry adds 0 to both totals. The sources do.

## `Q04.answer.cypher`

- `MATCH (p:Project) WHERE p.projectKey IN [...]`: every one of the seven projects is a
  row, whatever its issues hold (checklist item 4).
- First `CALL (p) { OPTIONAL MATCH (:Person)-[t:LOGGED_TIME]->(:Issue)-[:IN_PROJECT]->(p)
  WHERE t.seconds > 0 RETURN sum(t.seconds) AS logged }`: **step 2**, positive entries on
  the project's issues (checklist item 7), and **step 3**, their total. The `WHERE` sits
  inside the `OPTIONAL MATCH`, so a project with no entry still returns one row, and `sum`
  over no value is 0. Each relationship is one entry, summed once. The flagged bot set is
  empty for this corpus (spec 0006 AC-17), so no bot clause is written.
- Second `CALL (p) { OPTIONAL MATCH (i:Issue)-[:IN_PROJECT]->(p) WHERE
  i.timeOriginalEstimateS IS NOT NULL OR EXISTS { ... e.seconds > 0 } RETURN
  sum(coalesce(i.timeOriginalEstimateS, 0)) AS estimated }`: **step 1**, the population as
  read above, and **step 4**, the estimate total, a missing estimate as 0. Each total is
  computed in its own subquery, so no estimate is repeated once per entry (checklist
  item 5).
- `RETURN p.projectKey AS project_key, logged - estimated AS difference`: **step 5**, logged
  minus estimated, positive when logged time exceeded estimates.

The Q04 adapter turns each row into `project:<project_key>` with its `difference`. It adds
no project, fills no zero and does no arithmetic.

## `Q04.sources.1.cypher`

The known answer has one source step, with kinds `issue` and `time_entry`.

- `MATCH (i:Issue)-[:IN_PROJECT]->(p:Project)` with the population test of the answer
  file: **step 1**, every issue of the population, including those contributing zero.
- `OPTIONAL MATCH (:Person)-[t:LOGGED_TIME]->(i) WHERE t.seconds > 0`: **step 2**, every
  positive entry on the issue. For an issue with none, `t` is null and the row's
  `time_entry` cell is null, which under AC-12 as amended on 2026-11-12 is no ID and is
  skipped; the issue still counts in the `issue` column.
- `RETURN DISTINCT i.issueKey AS issue, t.historyId AS time_entry`: one row per positive
  entry, or one row for an issue with none; the `issue` column is read as a set.

These are the issues and entries whose amounts **step 3** and **step 4** sum and **step 5**
subtracts.

## The difference from the SQL pair

None in meaning. The graph computes each total in a `CALL (p)` subquery where SQL uses two
grouped steps and outer joins from `model.project`. A missing estimate is an absent
property here and NULL in SQL; both `coalesce` it to 0. In the sources, the graph's
`OPTIONAL MATCH` and SQL's outer join both leave a null `time_entry` for an issue with no
positive entry.
