# Q08 in Cypher, clause by clause

Question: which unresolved issues depend on other unresolved issues, and what are the
complete dependency chains connecting them?

The file reads the read only `neo4j` database: `Issue` nodes (`issueKey`,
`resolutionName`, absent when missing), their one `IN_PROJECT` relationship to a
`Project`, and the link relationships, which run from the outward side to the inward
side and carry `linkId` and `outwardLabel` (checklist item 8).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`:
ruling 1, a complete one hop chain counts (`hops = 2` is metadata and sets no minimum);
ruling 2, each hop's step lists `issue_link` plus both issues of that hop, and several
links between the same two issues stay one path with all their link IDs in that hop.

## The answer layout

A path answer (spec 0011 AC-12, amended 2026-11-12): one row per chain, a `path` column
with the issue keys in order, and one list column per kind with one item per hop:
`issue_link` holds each hop's link IDs, `issue` each hop's two issue keys. There is no
sources file. The Q08 adapter adds the `issue:` prefix to each path key and turns each
row into one step per hop; it sorts, filters and fills nothing.

## `Q08.answer.cypher`

- `MATCH p = (a:Issue)-[rs*1..5]->(b:Issue)`: **step 3**, paths followed in the outward
  direction, one to five hops, the question's `max_hops` (checklist item 9).
- `all(r IN rs WHERE r.outwardLabel = 'depends on')`: **step 2**, every hop is a link
  whose outward label is exactly `depends on`, whatever its type, as the reading note
  defines "depends on" by `type.outward`.
- `all(n IN nodes(p) WHERE coalesce(n.resolutionName, '') = '' AND EXISTS { ... })`:
  **step 1**, every issue on the path is unresolved (missing, null or exactly `""`,
  checklist item 6) and in one of the seven projects. This also makes both ends of every
  hop qualify, as step 2 asks.
- `all(k IN range(0, size(rs)) WHERE NOT nodes(p)[k] IN nodes(p)[k + 1..])`: no issue
  repeats (below).
- The two `NOT EXISTS { MATCH ... }` tests: **step 4**, complete chains only. The first
  refuses a path when a qualifying `depends on` link leads into its first issue from a
  qualifying issue not on the path, so no chain starts partway. The second refuses it
  when one leads out of its last issue to a qualifying issue not on the path. A one hop
  path passes both when nothing extends it (ruling 1).
- `WITH [n IN nodes(p) | n.issueKey] AS path, rs` then `UNWIND`, `collect(DISTINCT
  rs[h].linkId)` grouped by `path` and `h`: several links between the same two issues
  match as several paths over the same issues. They are one chain, and each hop keeps
  every link ID (ruling 2, checklist item 5).
- `RETURN path, [...] AS issue_link, [...] AS issue`: each hop's link IDs, looked up by
  hop number, and its two issues, in path order.

## How a repeated issue is forbidden

Cypher's default match mode forbids a repeated relationship in a path, not a repeated
node, so a cycle could otherwise come back to an issue. The query states it outright:
`all(k IN range(0, size(rs)) WHERE NOT nodes(p)[k] IN nodes(p)[k + 1..])` keeps a path
only when no issue appears again later in it. It does not rely on the `ACYCLIC` path mode
of Cypher 25 (spec 0008 Follow-up), because an explicit test reads the same on any
version. In step 4, `NOT u IN nodes(p)` and `NOT w IN nodes(p)` mean an extension back
onto the path does not count, so a chain that closes a loop is complete when nothing
else extends it, as the note's "without repeating an issue" says.

## How a chain past hop 5 is detected

The pattern stops at five hops, but step 4's second test looks one hop further: for a
five hop path it asks whether a qualifying link leaves the last issue for an issue not
on the path. If one does, the five hop path is a section of a longer chain and is left
out, which is what "a five-hop chain qualifies only if it cannot be extended" and
"exclude partial sections of longer chains" ask (checklist item 9). The first test does
the same at the start. A chain longer than five hops therefore returns nothing, never a
five hop piece of it.

## Checklist notes

No date bound applies (item 2), nothing is counted or summed (items 3, 7), no group is
listed (item 4). The only numbers are the cap, read from `max_hops`, and list positions;
no ID is written (item 10).

## The difference from the SQL pair

None in meaning. SQL builds the hop list first, merging several links into one hop, and
then walks it; the graph matches paths of relationships and merges paths with the same
issues afterwards. A missing resolution is an absent property here and NULL in SQL; both
read it with `coalesce(..., '') = ''`.
