# Q15 in Cypher, clause by clause

Question: what is the total logged hours on CLOUD-643 and all of its sub-tasks combined?

Both files read `Issue` nodes (`issueKey`), the `IN_PROJECT` relationship to `Project`
(`projectKey`), the `HAS_PARENT` relationship from a child `Issue` to its parent `Issue`,
and the `LOGGED_TIME` relationship from a `Person` to an `Issue` (`historyId`, signed
`seconds`).

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 4,
Q15 has one source step in every case, listing `issue`, `parent` and `time_entry`, even if
the total is 0 or a list is empty; the earlier ruling, reading B for every parent hop, so
the step adds kind `parent` holding the direct child keys; and the accepted plan, the scope
is all of CLOUD, the parent and the sub-tasks are conditions inside it, and an entry with
no author counts in hours. The standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q15.answer.cypher`

- `MATCH (p:Issue {issueKey: 'CLOUD-643'})-[:IN_PROJECT]->(:Project {projectKey:
  'CLOUD'})`: **step 1**, the parent record in CLOUD. `CLOUD-643` is named in the question,
  so the literal check allows it.
- `CALL (p) { RETURN p AS i UNION MATCH (c:Issue)-[:HAS_PARENT]->(p) RETURN c AS i }`:
  the parent itself, and **step 2**, every direct child, one `HAS_PARENT` hop only, so a
  grandchild never counts. `UNION` keeps each issue once.
- `OPTIONAL MATCH ()-[t:LOGGED_TIME]->(i) WHERE t.seconds > 0`: **step 3**, the positive
  entries on the parent and the children (checklist item 7). Each relationship ends at one
  issue, and each issue is one row, so no entry is counted twice (checklist item 5). The
  start node is left unnamed so no author condition is added: an entry with no author
  counts (the accepted plan), none exists in this corpus anyway (spec 0006 AC-16), and the
  flagged bot set is empty (spec 0006 AC-17).
- `RETURN coalesce(sum(t.seconds), 0) AS seconds`: **step 4**, the retained amounts summed,
  in seconds. `sum` skips the nulls the `OPTIONAL MATCH` leaves for an issue with no entry;
  the `coalesce` makes the total 0 when nothing matched at all, as the note says an issue
  with none contributes zero (checklist items 3 and 4).

The Q15 adapter returns the one `seconds` value. It adds and drops nothing.

## `Q15.sources.1.cypher`

The known answer has one source step, with kinds `issue`, `parent` and `time_entry`
(ruling 4).

- The first branch of the `CALL`: **step 1**, the parent's own record in `issue`, with a
  null `parent` cell, which under AC-12 as amended on 2026-11-12 is no ID.
- The second branch: **step 2**, each sub-task's record in `issue` and its parent hop in
  `parent` (the child key, reading B).
- `OPTIONAL MATCH ()-[t:LOGGED_TIME]->(i) WHERE t.seconds > 0`: **step 3**, every positive
  entry on the parent or a child, the entries whose amounts **step 4** sums. The `WHERE`
  sits inside the `OPTIONAL MATCH`, so an issue with no positive entry keeps a null
  `time_entry`, and if none has one the kind still comes back as `[]` (checklist item 11,
  ruling 4).
- `RETURN DISTINCT`: one row per issue and entry.

## Checklist notes

No date bound applies (item 2). The answer sums, the `coalesce` gives 0 for nothing found
(item 3). Missing, null and `""` do not arise: no key here can be empty, and a null
property is absent in the graph (spec 0008). No path is built, so item 9 does not apply.
No number is written; the one ID is the key the question names (item 10). Q15 is not zero
guarded, so it has no stage files (item 13).

## The difference from the SQL pair

None in meaning. SQL reads the parent hop from `parent_key` and keeps an issue with no
entry with a `LEFT JOIN`; the graph uses `HAS_PARENT` and an `OPTIONAL MATCH`.
