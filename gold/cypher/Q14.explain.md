# Q14 in Cypher, clause by clause

Question: is every sub-task of CLOV-538 resolved?

Both files read the read only `neo4j` database: `Issue` nodes (`issueKey`,
`resolutionName`, absent when missing), their one `IN_PROJECT` relationship to a
`Project`, and the `HAS_PARENT` relationship from a child `Issue` to its parent.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `1d793bd`: ruling
5, a parent hop adds the kind `parent` holding the direct child keys, and Q14 lists
`issue` and `parent`; ruling 7, Q14 reading A, if the answer is no the sources are `[]`
under AC-32, and AC-32 governs over the note's sentence on counterexamples; ruling 8, the
registered scope is all of CLOV.

## `Q14.answer.cypher`

- `OPTIONAL MATCH (p:Issue {issueKey: 'CLOV-538'})-[:IN_PROJECT]->(:Project {projectKey:
  'CLOV'})`: **step 1**, the parent record, optional so that the query still returns one
  row without it. `CLOV-538` is named in the question, so the literal check allows it.
- `OPTIONAL MATCH (c:Issue)-[:HAS_PARENT]->(p)` and `collect(DISTINCT c) AS children`:
  **step 2**, every direct child. The pattern is one relationship, so a grandchild never
  counts. `collect` skips the null of no child, so `children` is empty then.
- `size(children) > 0`: **step 2**, at least one direct sub-task exists, as the note
  requires.
- `all(child IN children WHERE coalesce(child.resolutionName, '') <> '')`: **step 3**,
  every child's resolution is present, not null and not `""` (checklist item 6).
- The `AND` of the two, `resolved`: **step 4**, the boolean, one row. With no sub-task, or
  no parent record, it is false, because the note's condition that a sub-task exists is
  not met (`all` over an empty list alone would say true).

The Q14 adapter takes the one `resolved` value. It changes nothing.

## `Q14.sources.1.cypher`

The known answer has one source step, with kinds `issue` and `parent`.

- The parent match and the children: **step 1** and **step 2**.
- `WHERE size(children) > 0 AND all(...)`: **step 3** and **step 4**, the same boolean as
  the answer file, so rows come back only when the answer is yes.
- `UNWIND [{issue: p.issueKey, parent: null}] + [child IN children | ...]`: the parent's
  own issue record in `issue` (its `parent` cell null, which under AC-12 as amended on
  2026-11-12 is no ID), and every direct child, resolved or not, its issue record in
  `issue` and its parent hop in `parent` (the child key, ruling 5). All children are
  listed, not an example, as the note says.
- When the answer is no, the file returns no rows, following ruling 7. With one sources
  file fixed by the layout, that is one step with both kinds empty rather than no step
  at all; this only matters if the answer is no.

## Checklist notes

No date bound applies (item 2). Nothing is counted or summed (item 3). No group is
listed (item 4). No path is built, so item 9 does not apply. The only number is the one
sub-task the note requires; the one ID is the key the question names (item 10).

## The difference from the SQL pair

None in meaning. SQL reads the parent hop as the child's `parent_key` column and decides
with `count(...) > 0 AND bool_and(...)`; a missing resolution is NULL there and an absent
property here, and both read it with `coalesce(..., '')`.
