# Q18 in Cypher, clause by clause

Question: which people appear in more than one project as reporter or assignee, and in
how many projects each?

Both files read `Issue` nodes (`issueKey`), the `IN_PROJECT` relationship to `Project`
(`projectKey`), and the `REPORTED_BY` and `ASSIGNED_TO` relationships from an `Issue` to
a `Person` (`personKey`), one for the current reporter and one for the current assignee.

## The rulings this pair follows

Your rulings of 2026-11-02, recorded in the body of main repo commit `25e339a`: ruling 2,
`project` is listed and holds the projects of the listed issues; ruling 3, `person` is
listed, returned people only, and Q18's one step lists `issue`, `person` and `project`.
The accepted plan: the scope is the seven projects, with the other conditions inside it.
The standing sources rule is in commits `2ecf29c` and `b13f405`.

## `Q18.answer.cypher`

- `MATCH (i:Issue)-[:IN_PROJECT]->(pr:Project) WHERE pr.projectKey IN [...]`: **step 1**,
  issues in the seven projects.
- `MATCH (i)-[:REPORTED_BY|ASSIGNED_TO]->(x:Person)`: **step 2**, the current reporter or
  assignee. A missing or `""` key has no relationship in the graph (spec 0006), so it is
  dropped as the note says (checklist item 6). The flagged bot set is empty (spec 0006
  AC-17), so no bot clause is written.
- `WITH x, count(DISTINCT pr) AS projects`: **step 3**, the distinct projects per person
  across both roles, so many issues or both roles in one project add one project
  (checklist item 5). `count`, never `sum` (checklist item 3).
- `WHERE projects >= 2`: **step 4**, at least two distinct projects.
- `RETURN x.personKey AS person_key, projects`: **step 5**, each person with their count.

The Q18 adapter turns each row into `(person:<person_key>, projects)`. It adds and drops
nothing.

## `Q18.sources.1.cypher`

The known answer has one source step, with kinds `issue`, `person` and `project`
(ruling 3).

- The first part repeats **step 1** to **step 4** and keeps the returned people.
- The second `MATCH (i:Issue)-[:REPORTED_BY|ASSIGNED_TO]->(x), (i)-[:IN_PROJECT]->(pr)`
  with the seven project filter: every issue where a returned person holds a qualifying
  role, with that person and the issue's project. Matching from the returned person,
  rather than listing every person on those issues, means a reporter or assignee who is
  not returned is never listed as a person (ruling 3). The projects are the projects of
  the listed issues (ruling 2). `RETURN DISTINCT` gives each (issue, person, project)
  once; the columns are read as sets.

## Checklist notes

No date bound applies (item 2). No hours (item 7). Item 4: a person with fewer than two
projects is not a member of the answer, so no zero rows are owed. No path is built
(item 9). No number or ID is written beyond the seven project keys and the `2` of "more
than one project", both from the reading note (item 10). The sources step is large;
it stays well below the 200,000 row cap (`STORE_ROW_CAP`).

## The difference from the SQL pair

None in meaning. SQL drops a NULL or `""` reporter or assignee key with `coalesce`; in
the graph such a key has no relationship. SQL merges the two roles with `UNION`; the
graph matches both relationship types in one pattern and counts distinct projects.
