# Q03 in Cypher, clause by clause

Question: how many issues resolved in FE between April 1 and June 30, 2012 (UTC) were
closed after their due date?

Every file reads the read only `neo4j` database: `Issue` nodes (resolution in
`resolutionName` and `resolutionDate`, due date in `dueAt`) and their one `IN_PROJECT`
relationship to a `Project`. Every datetime is stored in the `Z` form; a date only due
value was stored as midnight UTC at the start of that day by the load (spec 0006 AC-18),
which is exactly the reading note's rule. A missing value is an absent property, read as
null.

## `Q03.answer.cypher`

- `MATCH (i:Issue)-[:IN_PROJECT]->(p:Project) WHERE p.projectKey = 'FE'`: **step 1**, the
  FE population, each issue matched once.
- `i.resolutionName IS NOT NULL AND i.resolutionName <> ''`: **step 2**, a resolution name
  that exists and is not empty. No status condition (checklist item 6).
- `i.resolutionDate >= datetime('2012-04-01T00:00:00Z') AND i.resolutionDate <
  datetime('2012-07-01T00:00:00Z')`: **step 3**, the half open UTC interval in the `Z`
  form, never a named zone (checklist item 2). An absent resolution date compares as
  null and drops out.
- `i.dueAt IS NOT NULL AND i.resolutionDate > i.dueAt`: **step 4**, a present due date
  and a resolution strictly later than it.
- `RETURN count(DISTINCT i) AS issues`: **step 5**, each retained issue counted once;
  `count` gives 0 when nothing matches (checklist item 3).

The Q03 adapter reads the one row's `issues` value as the number. The known answer has no
source steps, so there are no sources files (checklist item 11).

## The stage files (the zero guard, checklist item 13)

`Q03.stage.1.cypher` to `Q03.stage.5.cypher` each return one integer, `issues`: the
store's own count of FE issues after the conditions of **step 1** up to **step n**, in the
order of the reading note, none added, dropped or merged.

- Stage 1: **step 1** only, every FE issue; it must be above 0.
- Stage 2: adds **step 2**. Stage 3: adds **step 3**. Stage 4: adds **step 4**.
- Stage 5: **step 5** adds no condition, so it holds the conditions of stage 4 and equals
  the answer file by construction.

The guard accepts the pair only when these five counts equal the SQL store's five.

## The difference from the SQL pair

None in meaning. The graph follows `IN_PROJECT` where SQL reads `project_key`, and a
missing value is an absent property where SQL has NULL; `IS NOT NULL` plus `<> ''` treat
both the same.
