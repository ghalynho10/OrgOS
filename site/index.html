Graph or SQL, and when? Conclusion of Phase 1

Ghaly Nicolas Jules
Code and eval: github.com/ghalynho10/OrgOS

This conclusion is about this project only. The counts were close, and where one store led, it was by a single question. In the counts, the biggest difference maker was not the store but the note. However, because too few questions disagreed, the test between the stores is inconclusive and therefore could not pick a winner.

5. How far this reaches

Limitations that matter most:

  1. The graph was built from tables designed in SQL, so it may be shaped like a database rather than a natural graph. That could disadvantage the graph.
  2. Every scored run got the reading note; real users don't write one, which is why I did the plain runs. Those still told the agent the answer's shape, unit and hop limit, which the scoring needed. A real person would give even less.
  3. The model ran on default settings with low thinking effort. More effort might change the results.

What a real deployment would need:

  1. This project loaded the data once; a real one would need constant updates.
  2. The same person appears under different names and emails in each system.
  3. Data sensitivity: a company could use its own model. Nothing in the project requires it to use Claude, though the numbers would need re-measuring on that model.
  4. Not everyone may see every ticket, and the agent would have to respect that.
  5. Real company data isn't only in Jira: there's chat, docs, code and HR systems.

Limitations

Group 1, from the scope

  • G1-1 known answers and dbt share one reading of the Jira fields scope feature 17, Done when
  • G1-2 the gold queries were model drafted blind to the answers, Q01 as a teaching pass, with counts only feedback, and Q01's pattern shaped the rest scope feature 17, Done when
  • G1-3 `model_int` is written in SQL, so the graph may lean relational. scope feature 17, Done when

Group 2, method

  • G2-1 n is 20, with 6 or 7 questions per type, so a test with fewer than 6 untied questions can never read `real`, and `did not detect a gap` is not `equal` spec 0014 AC-4, AC-6 and the reach table
  • G2-2 the family bound of AC-4 and the chance line of AC-7 spec 0014 AC-4 and AC-7
  • G2-3 the known answer code, the gold queries and the agent come from one model family, a shared blind spot and not a bias between stores spec 0014 rationale, Context (the literature look back, no longer in docs/session-notes.md)
  • G2-4 the strict score is all or nothing and not comparable to published execution accuracy spec 0014 rationale, Context; spec 0013 References (BIRD execution accuracy)
  • G2-5 query and run times are recorded but never compared or ranked, because both stores run untuned in Docker on one laptop on a small dataset (spec 0011 AC-24) spec 0011 AC-24
  • G2-6 every scored run got the reading note, and plain runs are a lower bound that still carried shape, unit and hop limit (spec 0013 Follow-up). spec 0013 Follow-up

OrgOS is a prototype of a system a company would build for itself. It tests one design question, a SQL store against a graph store for an AI agent over work data, with a frozen eval that checks citations. This page makes no claim that a company wants it and, like the conclusion above, names no winner.

The design specs behind this work are kept private. Where a limitation names a spec or a note, it points to a document that is not published here.

The data is The Public Jira Dataset (Zenodo record 15719919), licensed CC BY 4.0. Montgomery L, Lüders C, Maalej W. An Alternative Issue Tracking Dataset of Public Jira Repositories. In 2022 IEEE/ACM 19th International Conference on Mining Software Repositories (MSR) 2022 May 23 (pp. 73-77). IEEE.

The public code repository also holds test fixtures and a data description built from that dataset. They contain real looking names and email addresses from the dataset's change history, which are already public in the dataset. This page repeats none of them.
